## 1. 무엇을 만들고 있나

용병단을 이끌고 세계를 돌며 의뢰를 받아 성장하는 **브라우저 자동전투 판타지 RPG**.

- 용병단 = 부대 여러 개, 부대당 최대 7명
- 용병 등급 F~S, 도시 주점에서 **클래스를 지정해 고용하면 등급이 랜덤**으로 결정 (도박성이 핵심 재미)
- 전투는 자동. **아군 왼쪽 / 적군 오른쪽**, 캔버스 픽셀아트로 관전
- 1차 클래스 → 경험치 → 상위 클래스 **여러 후보 중 선택** 전직 (1→2→3차)
- 장비 파밍, 부대별 진형(골드/이벤트로 획득)
- 목표: 의뢰 반복 → 용병 성장 + 장비 파밍 → 용병단 강화

## 2. 기술 결정 (확정, 재논의 불필요)

| 항목 | 결정 |
|---|---|
| 플랫폼 | 브라우저. 순수 ES 모듈 + Canvas 2D. **빌드 스텝 없음, 외부 의존성 0** |
| 아트 | **절차 생성 픽셀아트**. 32×40 논리 픽셀, 화면에 3배 확대, `imageSmoothingEnabled=false` |
| 아트 방식 | 파츠 조합 리그 — 몸통/머리/투구/갑옷/망토/무기/방패 파츠를 조합 + 팔레트 스왑 + 프레임별 오프셋 애니메이션 |
| 렌더 | `ImageData` 버퍼 직접 쓰기 → 레시피 키 캐싱. 무기 회전은 픽셀 행렬 최근접 이웃(15° 배수), 캔버스 회전 금지 |
| 확장 | 나중에 진짜 스프라이트 시트를 구하면 `drawSpriteFrame` 하나만 교체하면 됨 |

> 사용자가 고른 것: 아트 방향 = 픽셀아트 스프라이트, 에셋 조달 = 우선 절차 생성.

## 3. 실행 방법

```bash
cd C:\claude\game && node tools/serve.mjs 5174
```
브라우저에서 `http://localhost:5174` 열기. (`.claude/launch.json` 에 `game` 설정이 있어 `preview_start` 로도 뜬다)

> **`python -m http.server` 를 쓰지 마라.** no-cache 헤더를 안 보내서 브라우저가 ES 모듈을 캐시한다.
> 소스를 고치고 새로고침해도 옛 코드가 돌아 "고쳤는데 왜 그대로지?" 로 시간을 태운다.
> `tools/serve.mjs` 는 항상 `no-store` 로 응답한다. 실제로 이 함정에 한 번 빠졌었다.
>
> 세이브도 같은 함정이다. 데이터 수치를 바꿨는데 반영이 안 되면 **localStorage 를 지우고 새 게임**을 시작해라
> (`state.quests` / 용병 HP / 의뢰 보상이 세이브에 박제되어 있다. 특히 `EXP_SCALE` 같은 보상 노브는
> 이미 생성된 의뢰에는 반영되지 않는다).
>
> **`state.save()` 는 `seed === 0` 인 시작 전 상태를 저장하지 않는다.** 일부러 넣은 가드다 —
> 없애면 이름 모달을 확정하기 전에 새로고침했을 때 빈 세이브가 박혀 단원 0명으로 부팅된다(§4 4차 세션).

### 브라우저 실행 검증 완료 (2차 세션)
게임을 실제로 띄워 확인했다. **런타임 크래시 없음, 콘솔 에러 없음.**
- 도시 화면 정상 (의뢰/주점/상점/부대 현황 전부 렌더링)
- 의뢰소 → 출정 → 전투 화면 진입 정상
- 스프라이트 파이프라인 정상: 아틀라스 768×40(24프레임), 프레임당 300~500픽셀,
  색상 13~20종(음영 있음), 바운딩 박스 머리 y=3 → 발 y=38, 공격 프레임은 무기가 앞으로 확장, 사망 프레임은 쓰러진 형태
- 렌더러+엔진 통합 정상: 실제 의뢰 전투를 끝까지 구동해 **아군 승리 38.4초**, 캔버스 100% 채워짐(색상 400종)

> **주의**: Browser 창이 표시되지 않으면 `document.hidden === true` 라서 `requestAnimationFrame` 이 멈춘다.
> 캔버스가 비어 보여도 게임 버그가 아니다. 검증하려면 창을 띄우거나, rAF를 우회해
> `b.step(1/60); r.update(1/60); r.draw();` 를 직접 루프로 돌려라.

### 밸런스 튜닝 완료 (2차 세션)
중단됐던 밸런스 작업을 이어받아 **초반이 클리어 불가능한 치명적 문제**를 발견하고 고쳤다.

| 증상 | 원인 | 수정 |
|---|---|---|
| 시작 부대 F랭크 승률 **0%** (3명 전멸, 적 0.6기만 사망) | `quest.js` 가 "아군은 항상 7인"이라 가정하고 적을 5~7기로 세웠는데 `newGame` 은 3명만 지급. 오토배틀러는 인원수가 곧 화력이라 개별 스탯 우위로는 못 이긴다 | 적 수를 랭크 비례로(F 3기 → A·S 7기), F랭크 1웨이브 고정, F 권장레벨 1~6 → 1~4, 시작 용병 3명 → 4명 |
| 전투가 3.6~5.1초에 끝남 (관전할 게 없음) | HP 대비 화력이 과함 | `classes.js` 에 `HP_SCALE = 2.6` 노브 신설. 양측이 같은 아키타입을 쓰므로 승률은 유지되고 전투 길이만 늘어난다 |

| E·D·C 보스전 승률 0% (보스 뜨면 자동 패배) | 보스는 일반 적의 5~8배 HP. 실측 E랭크 보스전 적 총HP가 아군의 **2.20배** | 낮은 랭크에서 보스 배율 damp(`BOSS_SCALE`) + F~C 보스 웨이브 호위 -2기 |
| 측정 자체가 틀렸음 | `earlygame.mjs` 가 `setSkillResolver` 미등록 → **모든 스킬이 무시된 채** 측정 | 등록 + 웨이브 HP 인계까지 실제 게임과 동일하게 맞춤 |

**RANK_LEVEL 재설계** (플레이어 요청): 각 랭크가 전직 차수 **하나 안에만** 들어가도록 잘랐다.
F[1-7] E[8-14] / D[15-24] C[25-34] / B[35-43] A[44-52] S[53-60].
이전에는 B[26-40]이 Lv35 경계를 관통해서 C를 맞추면 B가 무너지는 상태였다. 이제 랭크 하나 = 보정 하나로 대응된다.

### 4차 세션 — 파견(Dispatch) 시스템 + 경제 재밸런싱

플레이어 피드백: *"부대가 여러 개 있어도 하루에 하나만 가능해서 의미가 없다.
의뢰마다 걸리는 일자가 다르고, 일자는 직접 넘기는 게 낫겠다."*

#### 새 모델 (이게 지금 게임의 규칙이다)

- **전투와 보상은 즉시.** 출정하면 그 자리에서 관전하고 보상도 바로 받는다.
- **날짜는 자동으로 흐르지 않는다.** `applyQuestResult` 는 **`advanceDays` 를 부르지 않는다.**
  플레이어가 도시 화면의 `하루 넘기기` / `3일 넘기기` / `부대 복귀까지 넘기기` 로 직접 넘긴다.
  임금·부상 회복·의뢰 목록 갱신은 전부 `advanceDays` 안에서만 일어난다.
- **부대는 `quest.days` 만큼 잠긴다.** `Squad.status='away'`, `returnDay = day + quest.days`.
  잠긴 부대는 `canDeploy().ok === false` (`away:true`) 이고 `advanceDays` 가 복귀시킨다.
- **다른 부대는 같은 날 다른 의뢰에 보낼 수 있다.** 이게 부대를 여러 개 두는 이유다.
- 월드맵 이동은 계속 날짜를 소모한다. 원정 나간 부대가 있으면 `anySquadAway()` 로 경고한다.
  (부대는 도시를 따로 갖지 않으므로 같이 이동한 것으로 본다. 페널티 없음)

| 소요 일수 | F 1 / E 1~2 / D 2~3 / C 3~4 / B 4~5 / A 5~6 / S 6~7 (`quest.js RANK_DAYS`) |
|---|---|

**새 API** — `squad.js`: `SQUAD_IDLE/SQUAD_AWAY`, `normalizeDispatch(sq, day)`, `dispatchSquad(state, id, days)`,
`recallSquad`, `isSquadAway(sq, day)`, `squadReturnIn(sq, day)`, `canDeploy().{away,returnDay,returnIn}`.
`state.js`: `awaySquads(st)`, `anySquadAway(st)`, `daysUntilNextReturn(st)`, `advanceDays().returned`.
옛 세이브에 `status`/`returnDay` 가 없으면 전부 `idle` 로 정규화된다(스모크가 검사한다).

### 5차 세션 — 전투 연출: 화면 흔들림 제거 + 수동 종료

플레이어 피드백 두 줄이 전부였다:
*"흔들림은 빼는 게 나아 보인다. 다른 방법으로 임팩트를 주는 게 좋아 보이네"*
*"전투 화면은 사용자가 직접 클릭해서 끄는 게 나아 보인다"*

#### (1) 화면 흔들림 완전 제거 — 이게 지금 렌더러의 규칙이다

**화면 전체를 움직이는 연출은 하나도 없다.** 흔들림·줌 펀치·카메라 이동/회전 전부 없다.
`draw()` 의 카메라 변환은 항상 `setTransform(dpr,0,0,dpr,0,0)` 고정이다.
→ **새 연출을 넣을 때 이 규칙을 깨지 마라.** 화면을 미는 순간 플레이어가 다시 눈이 아프다고 한다.

대신 타격감은 전부 **국소** 연출로 낸다 (`renderer.js` 상단 "타격감 노브" 주석 참조):

| 연출 | 값 | 적용 범위 |
|---|---|---|
| 히트스톱 (주력) | 45ms · 치명타 110ms | 시뮬·파티클·팝업이 통째로 정지 |
| 실루엣 플래시 | 2프레임 (치명타 노란색 4프레임 / 사망 6프레임) | 맞는 유닛 1기 |
| 스케일 펀치 | +18% (치명타 +26%), 발밑 기준 | 맞는 유닛 1기 |
| 스프링 넉백 | 7px (치명타 14px), 탄성 복귀 | 맞는 유닛 1기 |
| 충격파 링 / 임팩트 / 무기 궤적 / 파편 | `art/fx.js` 의 `shockwave`/`impact`/`trail`/`shatter` | 타격 지점 주변 |
| 가장자리 비네트 펄스 | 치명타·사망 시. 실측 0.51회/초 | **색만** 변한다. 위치는 안 움직인다 |

`setShakeScale()` 은 **하위 호환용 빈 함수**로만 남아 있다 (`shakeScale` 은 항상 0).
호출부는 src 안에 없다. 되살리지 마라.

> ⚠ "모든 유닛이 동시에 펀치하면 화면이 흔들려 보인다"를 실측했다.
> 132 전투 / 168,224 틱에서 **3기 이상 동시 피격은 7틱(0.004%)** 뿐이고 최대 3기다.
> 1기 4.49% / 2기 0.20%. 지금 값이면 화면 흔들림처럼 보이지 않는다.
> 광역기를 늘리거나 펀치 진폭을 키울 거면 이 수치부터 다시 재라
> (재측정 스크립트는 `damage` 이벤트를 틱 단위로 묶어 서로 다른 targetUid 수를 세면 된다).

#### (2) 전투 화면은 클릭해야 넘어간다 — 자동 진행 경로 없음

- 웨이브가 끝나도 **전장은 그대로 살아 있다** (대기 모션 · 남은 파티클 · rAF 계속).
  엔진(`b.step`)만 멈춘 상태에서 진행 오버레이(`.bt-overlay.act`)만 뜬다.
- 다음 웨이브 / 결과 화면으로 가는 입력은 **클릭 · Enter · Space** 뿐이다.
- 연출 도중 클릭 = **연출만 건너뛴다.** 결과까지 한 번에 가지 않는다 (한 번 더 눌러야 한다).
- 결과 화면도 자동으로 닫히지 않는다. 하단 고정 `.bt-actions` 버튼을 눌러야 나간다.
- `ui/battle.js startLoop()` 의 `S.sinceFinish > 5` 는 **자동 진행이 아니다** —
  렌더러가 오류로 영영 `isSettled()` 를 못 돌려줄 때 **버튼만 대신 띄우는** 안전장치다.
- 렌더러 신규 API: `isSettled()` (마무리 연출까지 끝났는가), `skipEnding()` (UI가 넘겨받는다).

| `dispose()` 누수 | 전투 도중/대기 중 이탈 모두 **rAF 0 · keydown 리스너 0 · 전투 캔버스 제거** |
| 날짜 | 전투 전후 `state.day` 불변 (4차 세션 계약 유지) |
| 스모크 | `node tools/smoke.mjs` **125건 전부 통과** |

### 6차 세션 — 도시 평판 / 특화 도시 / 부대·정원 확장 / 일괄 해고

플레이어 요청 8건 중 5·6·7 이 서로 맞물려 있어서 **도시 평판**을 축으로 묶었다.
"부대가 커지면 5티어 도시에만 눌러앉는다"가 이번 설계가 푼 문제다.

#### (1) 도시 평판 (`state.reputation`) — 새 축

- 도시마다 0~100. **시작 도시만 10**, 나머지는 0 에서 시작한다.
- 의뢰 성공 `REP_QUEST_GAIN`(F+2 … S+10) 상승 / 실패는 그 절반(최소 1) 하락.
  `quest.js applyQuestResult` 가 `state.addRep` 을 한 번만 부르고 결과에 `rep` 을 실어 준다.
- **평판 10 미만이면 그 도시 주점에서 고용할 수 없다** (`canUseTavern`).
  낯선 도시에서는 의뢰부터 받아야 한다 → 이동에 "정착 비용"이 생겼다.
- 평판이 오르면 그 도시 주점의 **실효 티어**가 오른다 (평판 100 = +1.5 티어).
- **세이브 직렬화 대상.** 필드가 없는 옛 세이브는 "전 도시 0 + 시작 도시 10" 으로 정규화된다.

#### (2) 클래스 특화 도시 (`City.specialty`) — 저티어를 갈 이유

- 도시마다 1차 클래스 1~2종을 특화한다. 7종이 **정확히 3개 도시씩**(21칸) 나눠 갖고,
  특화 없는 도시는 없다. 7종 전부 tier 1~2 에 거점이 있다.
- 특화 클래스는 실효 티어 +1.0 **에 더해 S·A 가중치 ×4**(나머지는 비례 축소).
- ★ 설계 목표 달성: **1티어 특화 도시(평판 100) S 4.00% > 5티어 비특화(평판 10) S 3.00%.**
  → 부대가 커져도 저티어 특화 도시를 순회할 이유가 남는다.
  > 설계안은 ×3 이었는데 실측하니 정확히 **3.0% vs 3.0% 동률**로 목표가 깨졌다.
  > `merc.js SPECIALTY_TOP_MULT` 를 4 로 올려 해결했다. 이 값을 내리면 목표가 다시 깨진다 —
  > `tools/reputation.mjs` 가 매번 검사하니 건드리면 바로 FAIL 이 뜬다.

#### (3) 부대 5개 · 단원 정원 40 · 일괄 해고

| 항목 | 값 |
|---|---|
| 부대 (`squad.js MAX_SQUADS`) | 최대 5. 2번째 1,500G / 3번째 4,000G / 4번째 9,000G / 5번째 18,000G |
| 정원 (`state.rosterCap`) | 시작 20 → 최대 40, +5 단위. 25명 1,200G / 30명 3,000G / 35명 6,500G / 40명 12,000G |
| 일괄 해고 | `ui/company.js` 카드 체크박스 + `선택 해고` → 확인 모달(임금 절감·회수 장비 표기) |

- `createSquad(name, formationId)` 는 **시그니처·동작 그대로**(골드 안 받음).
  구매 경로는 `buySquad(state, name)` 를 쓴다 — 이걸 섞으면 부대가 공짜로 생긴다.
- 배치된 단원은 `[배치 인원도 선택]` 을 켜야 해고 대상으로 고를 수 있다(오조작 방지).

#### (4) 의뢰 공급을 부대 수에 비례시켰다

```js
count = clamp(3 + 부대수 * 2 + r.int(0,1), 4, 16)   // quest.js
```
- 부대 1개면 5~6건(예전과 거의 같다), 5부대면 13~14건.
- **상한을 12 → 16 으로 올린 건 실측 결과다.** 12 로는 5부대 유휴율이 15.6% 였다.
  원인을 쪼개 보니 유휴 31.2 부대-일 중 **"다른 부대가 먼저 채감"은 0.4건뿐**이고
  **"그 부대가 받을 수 있는 랭크가 목록에 안 남음"이 30.8건**이었다 —
  리롤 주기가 아니라 목록 길이가 병목이다. 16 으로 올려 12.8% 로 내렸다.
- 부대 1~3개는 생성 개수가 5~10건이라 상한에 닿지 않는다 = **기존 밸런스 불변**(실측 동일).

#### (5) 새 검증 도구 / 회귀 검사

```bash
node tools/smoke.mjs          # 184건 (평판/정원/부대확장/특화 59건 추가)
node tools/earlygame.mjs 24   # F~E + 파견루프 + 역경 + 1vs2부대 + 경제 + ★F 의뢰공급 + ★G 평판잠금
node tools/reputation.mjs     # ★신규 — 등급 분포 10만 회 롤 / 저티어 특화 우위 / 7종 배분 / 평판 속도
node tools/balance.mjs        # 랭크 승률 (변동 없음)
```
`tools/perf-battle.js` 는 **브라우저 전용** 성능 하네스다 (§9.5 참조).

### 7차 세션 — Lv80 · 4차 전직 105종 · 서브랭크 · 정예 · 난이도 상향 (검증·재밸런싱)

플레이어 피드백: *"성장이 금방 끝나고, 5등급 도시에서 대충 해도 다 깨진다. S 뽑기 말고 할 게 없다."*
7개 에이전트가 확장을 구현했고, 이번 세션은 **정합성 검증 + 전면 재밸런싱**을 맡았다.

#### (1) 정합성 — 4차 id 와 스킬 id
- classes_t4 담당과 skills 담당이 독립적으로 이름을 정했는데 **실제로는 어긋나지 않았다** —
  둘 다 `t4_<클래스id>` 규약을 지켰다(56종 전부 일치). 고칠 게 없었다. 스모크에 규약 검사 추가.
- `smoke.mjs` 를 105종·4차·`t4_<id>` 규약에 맞춰 갱신 → **187건 전부 통과**.
- `state.js DATA_VERSION` 2→3. 옛 세이브의 의뢰·주점·상점이 새 수치로 리롤된다.

#### (2) 측정 도구의 숨은 버그부터 잡았다 (이게 없었으면 전부 잘못 튜닝할 뻔했다)
- **`balance.mjs` 가 적 스탯 파이프라인을 통째로 무시하고 있었다.** `waveEnemyDefs` 가
  `enemyStats(레벨만)` 만 써서 `wave.power`(RANK_POWER×레벨초과분)·보스감쇠·정예를 안 붙였다 —
  그래서 RANK_POWER 를 바꿔도 측정값이 안 움직였다. `quest.js enemyUnitDefs` 를 export 해
  실제 게임과 같은 경로로 재게 고쳤다.
- **서브랭크·정예 버킷 비교는 표본 교란이 컸다** (정예 풀 vs 일반 풀은 적 구성·보스가 다르다).
  → **같은 의뢰에 플래그만 토글하는 통제 비교**로 바꿨다(정예 ON/OFF, 서브랭크 배율만 교체).
- **S 는 표본 편차가 커서** 60라운드 소표본이 ±15%p 흔들렸다 → 전 섹션을 **공용 대형 풀**로
  통일하고 기본 표본을 40→90 으로 올렸다. `sectionQuests` 는 **비정예만** 재도록 고쳤다
  (정예를 섞으면 기본 대역이 정예 하락분에 오염돼 실제보다 쉬워 보인다 — S 가 68% 인데 53% 로 보였다).

#### (3) 난이도 재밸런싱 (설계 F) — `quest.js` 노브만 건드렸다. 전투 공식·클래스 스탯은 불변.
- **보스 노출을 낮췄다**: `BOSS_CHANCE` B·A·S 0.60 → **0.35**. 0.60 이면 고랭크의 60%가 보스전이라
  승패가 이분법이 되어 랭크·서브랭크·정예 어느 노브를 건드려도 승률이 한꺼번에 뒤집혔다(B·A 가
  6% 배율에 ±30%p). 낮추니 세 축이 안정적으로 튜닝됐다.
- **`RANK_POWER`(적 전스탯 배율)로 대역을 맞췄다**: `[1.00, 1.04, 1.14, 1.12, 1.09, 1.06, 1.08]`.
  `RANK_CREEP=[0,5,2,0,0,1,2]`, `PROMO_STEP=[0,0,4,4,2,8,13]`, `BOSS_SCALE B/A/S=0.80/0.85/0.90`.
- **A 는 구조적 칼끝**이다(3차 부대 vs 2배 센 tier4 적 풀). 배율에 극도로 민감해 가장 손이 많이 갔다.
- **서브랭크는 레벨/적수 델타를 버리고 `SUB_POWER`(레벨 상한 무관 스탯 배율)로 바꿨다**:
  원안(+3레벨·+1적)은 저랭크에서 -40~60%p 로 과했고 S(적수 상한·Lv80 상한)에선 오히려 +쪽이
  더 쉬워졌다(S+ 역전). `SUB_POWER={-1:0.975, 0:1, 1:1.032}` 로 전 랭크 균일하게 갈랐다.
- **정예는 ×1.30(전원)+×1.60(챔피언)이 실효 ~1.7배라 승률을 0~4%로 짓밟았다** → `ELITE_MULT 1.035`·
  `ELITE_CHAMP_MULT 1.10` 으로 낮춰 평균 -22%p(목표 18~28) 로 맞췄다.
  > ⚠ 승률 곡선 기울기가 랭크마다 달라(50% 부근이 가장 급) 정예·서브랭크의 **정확한 %p 를 전 랭크에서
  > 동시에 맞추는 건 물리적으로 불가능**하다(D 완만 -11 ~ A 급 -31). balance.mjs 판정을 **방향 전 랭크
  > 준수 + 평균이 목표 대역** 으로 짰다. 표에 랭크별 실측값을 그대로 보고한다.

#### (4) 경험치 곡선 — 도시 이동을 넣어 재측정 (HANDOFF 미해결 항목 해소)
- 설계 원안(`60·lv^1.72`·`EXP_SCALE 1.8`)은 **도시 이동을 넣은** 실측에서 목표보다 ~2배 느렸고,
  특히 지수 1.72 가 후반(Lv35·55)을 과하게 늘렸다. **지수 1.72→1.55, EXP_SCALE 1.8→2.45** 로 조정.
- `earlygame.mjs` 에 **★E2 성장 곡선(도시 이동 포함)** 섹션을 신설했다. 부대가 크면 상위 tier 도시로
  이동(travelDays 소모)하며 자기 레벨에 맞는 랭크를 받는다. **10시드 전부 Lv80 도달**.
- 성장 노브는 전투 밸런스와 **독립**(전투는 레벨 대 레벨)이라 난이도 튜닝을 건드리지 않는다.

## 6. 다음 세션 작업 순서 (권장)

1. **Browser 창을 띄운 상태로** 게임을 열고 전투 화면 스크린샷을 사용자에게 보여줘라.
   **도트 퀄리티 판정을 아직 못 받았다.** 창이 닫혀 있으면 rAF가 멈춰 스크린샷을 못 찍는다.
   마음에 안 든다고 하면 무료 에셋팩/AI 생성 스프라이트로 교체 (`drawSpriteFrame` 이 교체 지점)
2. 게임 루프 한 바퀴 수동 플레이: 주점 고용(등급 랜덤 연출) → 부대 편성/진형 → 의뢰 수주 →
   전투 관전 → 보상/레벨업 → **전직 선택 UI** → 장비 장착 → 도시 이동.
   화면별 상호작용(드래그 편성, 전직 카드 비교, 아이템 비교 툴팁)은 아직 손으로 눌러보지 않았다.
   **파견 경로는 4차 세션에서 브라우저로 확인했다**: 새 게임 → 의뢰 출정 → 즉시 보상 →
   부대 `away`(복귀 5일차) → 날짜 그대로(4일차) → `부대 복귀까지 (3일)` 클릭 → 임금 60G 차감 후 복귀.
   **부대를 2개로 나눠 같은 날 둘 다 출정시키는 것은 아직 손으로 안 눌러 봤다** (시뮬로만 검증).
3. 남은 밸런스 항목 §7 참고. **`balance.mjs` 2번 섹션 잣대부터 결정할 것.**
4. 회귀 확인: `node tools/smoke.mjs && node tools/earlygame.mjs 24 && node tools/reputation.mjs`
5. **★ 전투 프레임 성능을 "보이는 창"에서 다시 재라 (§9.5).** 6차 세션에서는 브라우저 창이
   숨겨져 있어(`document.hidden === true`) 같은 코드가 페이지 세션마다 **p95 12ms ↔ 32ms** 로
   2배 넘게 흔들렸다. 목표(p95 < 12ms · max < 25ms)를 **확인하지 못했다.**
   하네스와 방법은 이미 `tools/perf-battle.js` 에 있다 — 창을 띄우고 `run()` 만 부르면 된다.

### 9.5 ★ 전투 프레임 성능 — **목표를 확인하지 못했다**

목표는 7대7 전투에서 **프레임 시간 p95 < 12ms · max < 25ms**. 하네스(`tools/perf-battle.js`)를
새로 만들어 `ui/battle.js` 와 **같은 순서**(update → step → drainEvents → draw)로 수동 펌프하고,
캔버스 2D 가 명령을 모아 뒀다 나중에 래스터하므로 프레임 끝에서 `getImageData(0,0,1,1)` 로
**강제로 끝낸 뒤** 시간을 쟀다(이걸 빼면 p50 이 0.3ms 로 나오고 뒤늦게 294ms 짜리 스톨이 터진다).
표본은 **전투 중 프레임만** 센다(끝난 뒤 프레임은 유닛도 파티클도 없어 값이 싸다).

**결과: 같은 코드·같은 기계인데 페이지 세션마다 2배 넘게 흔들렸다.**

| 측정 | p50 | p95 | max | 표본 |
|---|---|---|---|---|
| dpr1 · 세션 A (5라운드) | 5.9~6.1ms | **12.4~14.1ms** | 40~77ms | 라운드당 4,917 프레임 |
| dpr1 · 세션 B (4라운드) | 10.4~11.1ms | **29.5~32.0ms** | 80~254ms | 라운드당 4,917 프레임 |
| dpr2 · 세션 B (2라운드) | 21.9~22.7ms | 56.8~56.9ms | 122~142ms | 라운드당 4,917 프레임 |

같은 세션 안에서는 라운드 간 편차가 작다(p95 ±1.5ms). **세션 간 차이가 2배**다.
→ 이 수치로는 "p95 < 12ms" 를 통과라고도 미달이라고도 말할 수 없다.

**흔들리지 않은 것 — 렌더러 단계별 비용** (`r.__prof`, 스프라이트 캐시를 비운 직후, 두 세션에서 동일)

| 단계 | dpr1 | dpr2 |
|---|---|---|
| 합계 | **5.8~6.1ms** | **11.5ms** |
| bg (배경 blit) | 1.20~1.24 | 1.11 |
| fx (파티클) | 0.98~1.05 | 0.60 |
| units (유닛 14기) | 0.85~0.94 | 7.09 ※ |
| pops (데미지 숫자) | 0.71~0.79 | 0.42 |
| vignette / edge / rings / plates / hud | 각 0.29~0.48 | 각 0.25~1.04 |

※ dpr2 의 units 7.09ms 는 **스프라이트 캐시가 커진 상태**에서 잰 값이다. 아래 참조.

**측정 중에 나온 별개의 관찰 (원인 미확정, 재현이 불안정)**

- 14기 스프라이트 blit 는 캐시가 작을 때 **0.33ms**, 스프라이트가 80개 넘게 쌓인 뒤 특정
  아틀라스에서 **6.5ms** 로 튀는 경우를 봤다(같은 픽셀을 새 캔버스에 복사하면 다시 0.34ms).
- 다만 "시드마다 캐시를 비우고 재기 vs 그대로 두고 재기" 로 **직접 A/B** 했을 때는
  p95 13.0 vs 14.3ms 로 차이가 작았다. 즉 **캐시 크기가 주범이라고 단정할 근거가 부족하다.**
- `spriteCache` 는 지금 **상한이 없다**. 로스터 40명 + 적 다양성 + UI 화면까지 더하면
  실제 세션에서도 100개를 쉽게 넘는다. 상한(LRU)을 두는 건 어차피 메모리 위생상 옳지만,
  **성능 이득을 측정으로 증명하지 못해 이번에는 건드리지 않았다.**

**다음 담당자에게**

```js
// 개발 서버를 띄우고, 브라우저 창이 실제로 보이는 상태에서:
const m = await import('/tools/perf-battle.js');
m.run({ frames: 900 });      // 10시드 · 전투 중 프레임만 · {p50,p95,p99,max,pass}
m.profile({ frames: 300 });  // 단계별 ms/프레임
```
1. **창을 띄운 채로** 위를 3회 이상 돌려 세션 간 편차부터 확인해라. 편차가 여전히 2배면
   이 기계/브라우저로는 판정할 수 없다는 뜻이니 다른 측정 방법을 찾아야 한다.
2. 편차가 잡히고도 p95 가 12ms 를 넘으면 `bg`(1.2ms) 와 `fx`+`pops`(1.7ms) 부터 봐라 —
   단계 프로파일상 단일 지배 항목은 없고 비용이 고르게 퍼져 있다.
3. dpr2 는 dpr1 의 **약 2배**다. HiDPI 화면이 기준이면 목표치를 그쪽에서 잡아야 한다.
   `renderer.js` 는 `devicePixelRatio` 를 [1,2] 로 clamp 한다 —
   테스트에서는 `Object.defineProperty(window,'devicePixelRatio',{value:2})` 로 강제할 수 있다.

`node tools/earlygame.mjs 24` → **exit 0** (F랭크 **92.8%** / 출전 불가 **0회** / 5부대 유휴율 12.5%).
`node tools/reputation.mjs` → **exit 0**.

**왜 안 흔들렸나 — 그리고 이게 왜 좋은 소식만은 아닌가**

- `balance.mjs` 의 랭크 승률은 **장비를 뺀 부대**로 잰다(`equipment:{}`). 즉 `SLOT_POWER` 를
  어떻게 잡아도 그 표는 움직이지 않는다. 슬롯 3→10 이 랭크 대역을 깨뜨릴 수 없는 구조다.
- 장비를 낀 부대로 S랭크 비정예 의뢰를 재 보면(표본 150, Lv80 4차 grade B 7인):

| 부대 | S랭크 승률 | 전투력 지수 |
|---|---|---|
| 장비 없음 (= balance.mjs 잣대) | 86.0% | 18,441 |
| **옛 3슬롯 전설 ilvl80** | **100.0%** | 28,213 |
| 10슬롯 전설 ilvl80 | 100.0% | 36,865 |
| 풀 신화세트 | 100.0% | 52,397 |

  → **10슬롯이 의뢰 밸런스를 깬 게 아니다. 옛 3슬롯 시절에도 이미 100% 였다.**
  "만렙 장비를 갖추면 의뢰는 다 깬다" 는 6차부터 있던 성질이고, 이번 확장이 만든 문제가 아니다.
  그래서 `SLOT_POWER` 를 설계값(합계 4.70)에서 내리지 않았다 — 내리면 랭크 대역은 그대로인 채
  **플레이어 체감만 나빠진다**.
- 대신 장비 총량은 `tools/dungeon.mjs` 1번 섹션이 매번 찍는다:
  **장비없음 1.00 → 전설 10칸 1.83 → 풀세트 2.45 (전설 대비 x1.34).**
  이 배수가 던전 곡선의 기준이다. `SLOT_POWER` 를 만지면 던전 곡선을 반드시 다시 재라.

### 11.4 ★ 던전 난이도 — `tools/dungeon.mjs` (신규)

```bash
node tools/dungeon.mjs                 # 기본 표본
node tools/dungeon.mjs --n=24 --nrun=24  # 정밀
```
1) 장비 구성별 부대 전투력 2) 만피 기준 웨이브별 승률 3) **런(HP 인계) 도달 웨이브** 4) 목표 판정.
세트는 "네 던전을 다 돌아 각자 자기 계열 세트를 입은" 상태로 모델링한다
(던전 1~3 은 2/7 명만 착용 가능하므로 이 모델은 **낙관적**이다 — 실제 게임은 이보다 빡빡하다).

**측정에서 먼저 알아낸 두 가지 (이걸 모르면 잘못 튜닝한다)**

1. **웨이브 하나의 승률은 계단이다.** 편성이 고정(`lineup`/`bosses`)이라 7대7 만렙 전투는
   거의 결정론이다. 실측: 배율 3.0 → 100% / 3.2 → 8% / 3.5 → 0%. **0.1 이 40~90%p.**
   "1웨이브 승률 50%" 같은 값에 맞추는 것은 물리적으로 불가능하다 →
   **판정은 전부 런(HP 인계) 통계로 바꿨다.**
2. ★ **드랍 게이트가 곧 진행 조건이다.** 방어구는 1~5웨, 장신구는 6~8웨, 무기·왼손은 9~10웨에서만
   나온다. 처음에 설계대로 "세트 0개 = 1웨이브 50%" 로 맞춰 봤더니
   **방어구 5칸을 다 모은 부대도 2웨이브에서 멈춰 장신구를 영원히 못 얻는** 순환 고리가 생겼다(실측).
   그래서 **1~9웨이브는 완만하게 두고 10웨이브만 벽**으로 만들었다.

```js
// game/dungeon.js
export const WAVE_POWER = [2.68, 2.70, 2.72, 2.74, 2.76, 2.80, 2.90, 3.05, 3.30, 4.78];
// data/dungeons.js — 던전별 정규화 (전설 10칸 부대의 1웨이브 50% 지점을 서로 맞춘 값)
frostbastion 0.929 / bloodarena 1.043 / starfall_spire 0.938 / astral_temple 1.109
```

`sets.js` 의 5단계·7단계 보너스도 **총합을 유지한 채** 5쪽으로 옮겼다(5단계가 사실상 무의미해
set3 → set5 가 +1.5% 밖에 안 됐다). 3/5/7/full 총합은 그대로라 풀세트 성능은 변하지 않는다.

**실측 — 런(HP 인계, 1웨이브부터 연속) · 던전 4개 × 20시드 = 80런**

| 장비 | 평균 도달 | 1웨↑ | 2웨↑ | 3웨↑ | 5웨↑ | 7웨↑ | **10웨 완주** |
|---|---|---|---|---|---|---|---|
| 장비없음 | 0.0 | 0% | 0% | 0% | 0% | 0% | 0% |
| **전설10 (세트 0개)** | **1.8** | 100% | 75% | 0% | 0% | 0% | 0% |
| 세트3 | 2.9 | 100% | 100% | 76% | 0% | 0% | 0% |
| 세트5 (방어구 전부) | **5.4** | 100% | 100% | 100% | 89% | 1% | 0% |
| 세트7 | 7.8 | 100% | 100% | 100% | 100% | 78% | 0% |
| 세트8 (방어구+장신구) | **8.2** | 100% | 100% | 100% | 100% | 100% | 0% |
| **풀세트(10)** | **9.3** | 100% | 100% | 100% | 100% | 100% | **30%** |

판정 (전부 `tools/dungeon.mjs` 가 매번 검사):

| 항목 | 결과 |

**★ 목표를 못 맞춘 항목 (숨기지 않는다)**

- 설계 목표 **"세트 0개 → 1웨이브 승률 ~50% / 2웨이브 <10%"** 는 **미달**이다.
  실측은 1웨이브 100% / 2웨이브 75% (평균 도달 1.8웨이브)다.
- 이유: 1웨이브를 50% 로 맞추려면 곡선 전체를 +23% 올려야 하는데,
  그러면 **방어구 5칸 부대가 6웨이브에 못 닿아 장신구·무기를 영원히 못 얻는다**(실측으로 확인).
  둘 중 하나만 고를 수 있어서 **"세트를 완성할 수 있다"** 를 택했다.
- 다시 맞추고 싶으면 곡선이 아니라 **세트 단계별 성능 폭**을 넓혀야 한다
  (`sets.js SLOT_COEF` 를 올리고 `items.js SLOT_POWER` 를 내려 전설 대비 세트 우위를 키우는 방향).
  그러면 랭크 밸런스(장비 낀 실제 플레이)도 같이 움직이므로 §11.3 표를 다시 재야 한다.

## 12. 9차 세션 — 세트 고유 효과를 실제로 전투에 붙였다 (검증·재밸런싱)

8차가 남긴 미해결 항목(§11.6 마지막)이 이번 세션의 전부다:
**`data/sets.js` 의 고유 효과 4종이 전투에 아무 영향도 주지 않았다.**
`setBonusAt().specials` 까지는 살아 있었지만 `quest.js`/`squad.js` 가 `UnitDef` 에 싣지 않았고
`battle/engine.js` 에는 `special` 이라는 단어조차 없었다. 그런데 화면(`ui/company.js`)에는
"전투를 시작할 때 최대 체력의 25%인 방어막을 …" 이라고 **떠 있었다** — 플레이어에게 거짓말이었다.

4개 에이전트가 엔진 훅·배선·정의 통일을 구현했고, 이 세션은 **측정 증명 + 던전 재밸런싱**을 맡았다.

### 12.1 ★ 정말 적용되는가 — `tools/setspecial.mjs` (신규)

```bash
node tools/setspecial.mjs                 # 전 섹션 (기본 표본 n=30)
node tools/setspecial.mjs --only=wire     # 배선만
node tools/setspecial.mjs --n=16          # 빠르게
```

여섯 섹션 전부 통과(exit 0). **말이 아니라 같은 시드에서 ON/OFF 를 토글한 실측이다.**

| 섹션 | 검사 |
|---|---|
| 0. 어휘 일치 | `sets.SET_SPECIAL_IDS`(4) ↔ `engine.SPECIAL_IDS`(4) **양방향**. 미구현·유령 0 |
| 1. 배선 | `squad.squadUnitDefs` / `quest.questBattleDefs` / `dungeon.dungeonBattleDefs` **세 경로 전부** 실림. 셋의 효과 목록이 동일. **적에게는 안 실림.** `params` 가 sets.js 원본과 동일 |
| 2. 훅 단위 | 4종 14건 — 방어막 수치·지속, 파괴 시 아군 버프, 1회 제한, 흡혈률, 쿨감, 중첩 상한, 분열타 피해 기준, 근접 미발동, 게이지 충전, 부활 HP, 아군 회복, 부활 1회 |
| 3. ON/OFF | 던전 런(HP 인계) 120런 |
| 4. 개별 기여도 | 4종을 하나씩만 켠 값 + **발동 횟수 실측** |
| 5. 결정론 | 같은 시드 두 번 = 같은 결과 (64쌍) · 다른 시드는 다른 결과 |

**★ ON/OFF — 같은 시드·같은 부대(Lv80 4차 7인 풀세트) · 던전 4개 × 30런**

| 구성 | 웨이브 승률 | 평균 피해/웨이브 | 평균 생존 | 평균 도달 | 10웨 완주 |
|---|---|---|---|---|---|
| 고유효과 OFF | 90.0% | 377,234 | 7.00 | 9.00 | **0.0%** |
| 고유효과 ON | 93.3% | 403,318 | 6.86 | 9.33 | **33.3%** |
| 차이 | **+3.3%p** | **+26,084 (+6.9%)** | −0.14 | +0.33 | **+33.3%p** |

> 「평균 생존」이 −0.14 인 건 효과가 나빠서가 아니다. ON 은 **10웨이브(벽)까지 들어가서** 거기서
> 사람이 죽고, OFF 는 애초에 10웨이브를 못 밟는다. 도달·완주가 진짜 지표다.

**★ 개별 기여도 — 10웨이브 벽에서의 마진** (마진 = 아군 잔여HP% − 적 잔여HP%)

던전은 편성이 고정이라 웨이브 하나의 승률이 **계단**이다(§11.4). 그래서 "하나만 켠" 값은
승패가 아니라 **마진**으로 잰다 — 벽은 넷을 다 켜야 넘어가도록 맞춰 뒀기 때문이다.

| 효과 | id | 승률 | 마진 | Δ마진 | 발동 횟수(웨이브당) | 훅 |
|---|---|---|---|---|---|---|
| (전부 OFF) | — | 0.0% | −47.4% | — | — | — |
| 피의 갈증 | `bloodoath_frenzy` | 0.0% | −46.4% | +1.0%p | **26.03** | dealDamage 26,095 · kill 5,139 |
| 성좌의 은총 | `constellation_grace` | 0.0% | −47.3% | +0.1%p | **0.07** | lethal 80 |
| 불락의 가호 | `rampart_aegis` | 0.8% | −38.3% | **+9.1%p** | **2.49** | battleStart 2,400 · shieldBreak 593 |
| 유성 낙하 | `starseeker_starfall` | 0.8% | −35.2% | **+12.1%p** | **111.52** | dealDamage 131,313 · kill 2,513 |
| **(전부 ON)** | — | **27.5%** | **−12.5%** | **+34.9%p** | — | — |

- **발동 횟수는 추정이 아니다.** 엔진 `applySpecial` 이 발동할 때마다
  `unit.specialState[id].fired` / `fired_<hook>` 를 올리고 도구가 그걸 그대로 읽는다.
  **4종 전부 0 이 아니다** = 죽은 효과 없음.
- 넷을 합치면 +34.9%p 로 **개별 합(+22.3%p)보다 크다** — 방어막이 버티는 동안 분열타가 적을
  깎고, 그만큼 부활·흡혈이 더 오래 굴러가는 상승 작용이다.
- `constellation_grace` 가 작은 건 모델 탓이다. "각자 자기 계열 세트"라 **7명 중 힐러 1명만** 갖는다.

  **개별 기여도 표의 눈금이 통째로 바뀐다** — 마진 기준으로 다시 봐라.
- **8차의 "세트 0개 → 1웨이브 승률 ~50%" 목표는 9차에도 미달**이다(실측 100%/2웨 75%).
  §11.4 마지막 항목 그대로 — 곡선이 아니라 **세트 단계별 성능 폭**으로 풀어야 한다.
- **`tools/dungeon.mjs` 의 세트 모델은 여전히 낙관적이다**(§11.6). 고유 효과가 붙으면서
  낙관 폭이 더 커졌다 — 던전 1~3 세트는 7명 중 2명만 착용 가능한데 그 2명이 고유 효과까지 받는다.
  던전별로 "그 던전 세트만 모은 부대"를 재는 섹션이 있으면 더 정확하다.
- **`balance.mjs` 2번(클래스 기여도) FAIL 은 9차에도 그대로다** — §7 의 방법론 문제.
- **전투 프레임 성능(§9.5)은 9차에도 미측정** — 여전히 열려 있다.
  참고로 고유 효과는 프레임 비용을 늘렸을 수 있다(유성 낙하가 **웨이브당 111회** 추가 피해를
  만든다 = damage 이벤트·파티클이 그만큼 늘어난다). §9.5 를 다시 잴 때 **풀세트 부대로** 재라.
- `sets.js` 의 `SPECIAL_TRIGGERS` 에는 5종이 있지만 실제로 쓰이는 건 4종이다
  (`onKill`/`hit` 은 엔진 훅 이름 `kill`/`dealDamage` 로 매핑된다). 새 효과를 넣을 땐
  SPEC §5.5 의 훅 표와 `sets.js` 의 trigger 어휘를 **둘 다** 갱신해라.

### 13.1 기준 뷰포트와 판정 방법 (★ 다음 담당자는 여기부터 읽어라)

| 뷰포트 | 뭘 보는가 |
|---|---|
| **360 x 800** | 안드로이드 보급형. **가장 좁은 기준** — 여기서 되면 대부분 된다 |
| **390 x 844** | iPhone |
| **767 x 900** | 모바일 셸의 **마지막 픽셀**. 브레이크포인트 경계 검사용(§13.3) |
| **768 x 1024** | 태블릿 세로 |
| **1280 x 800** | **PC 기준선. 여기가 나빠지면 실패다** |

**판정 5가지** (`tools/mobileaudit.js` 가 전부 잰다)

1. **가로 스크롤 0** — `document.body.scrollWidth <= innerWidth`. **이게 가장 중요한 판정이다.**
   `overflow-x:hidden` 으로 덮지 마라 — 내용이 잘려 못 쓰게 된다. 원인을 고쳐라.
2. **화면 밖 요소 0** — `getBoundingClientRect().right > innerWidth`.
   단, 조상이 `overflow-x:auto` 면 그 안에서 스크롤되는 것이므로 정상이다(넓은 표의 정석 패턴).
3. **터치 타겟 ≥ 36px** — 단, **실효 히트 영역**으로 잰다. 체크박스가 22px 라도 감싼 `<label>`
   이 40px 이면 통과다(실제로 `.co-cb` 22px / `.co-chk` 40px 가 그 경우였다).
4. **글자 ≥ 12px** — **폰 폭(≤767px)에서만** 판정한다. 768px 이상은 PC 설계의 9~11px 라벨이 정상이다.
5. **콘솔 에러 0.**

**두 개의 도구**

```bash
node tools/mobile.mjs             # 정적 검사 (뷰포트 없이 소스만 읽는다). 실패 시 exit 1
node tools/mobile.mjs --verbose   # 통과 항목까지 전부
```
`css/style.css` + `src/ui/*.js` 의 **템플릿 리터럴 CSS** 를 파싱해 741개 룰을 검사한다.
A 고정 px 폭 / B `position:sticky` / C 터치 타겟 / D 글자 하한 / E 캔버스 스케일 / F **JS 인라인 스타일**.
정적 검사가 알 수 없는 것(DOM 중첩, JS 분기)은 **`mobile-ok:` 주석 + 이유**로 면제한다 — 현재 12건.

### 13.4 PC 회귀 — **1280px 는 바뀌지 않았다** (증명)

전체 스타일시트의 `@media` 25개를 열거해 `matchMedia().matches` 를 찍었다.
**1280px 에서 참인 것은 `(min-width: 1000px)` 2개뿐** — 둘 다 8차부터 있던 `company-style` 규칙이다.
모바일(≤767)·태블릿(768~1024) 쿼리는 **하나도 걸리지 않는다.**

미디어쿼리 밖에서 바뀐 규칙은 **`.modal.wide` 단 하나**이고, 1280px 실측값이 그대로다:
`min-width: min(760px,100%)` → **width 760px · left 255 · right 1015** (layer 1270 / padding 24).

### 13.5 규약 (다음 담당자가 지켜야 하는 것)

1. **폰 기준선은 767px 하나다.** `css/style.css` · 모든 `ui/*.js` · JS 의 `isNarrow()` 가 전부 같은 값이다.
   여기서 어긋나면 §13.3 의 "버튼이 내비 뒤로 숨는" 종류의 버그가 **반드시** 다시 난다.
2. 화면 모듈은 `css/style.css` 를 고치지 말고 자기 모듈 안에 `<style>` 을 1회 주입한다.
   반응형 규칙은 **전부 `@media` 안에만** 넣는다(PC 를 건드리면 안 된다).
3. 넓은 표/블록은 `overflow-x:auto` 래퍼 안에 넣는다 — 페이지가 아니라 그 안에서 스크롤시킨다
   (`.table-wrap` · `.city-tablewrap` · `.bt-tablewrap` · `.dg-stairs-wrap`).
4. **JS 인라인 스타일에 고정 px 폭을 넣지 마라.** 인라인은 미디어쿼리로 못 덮는다
   (`tools/mobile.mjs` F 항목이 검사한다). 필요하면 클래스로 빼라 — `.modal.wide` 가 그래서 옮겨졌다.
5. hover 에만 있는 정보를 만들지 마라. 폰에는 hover 가 없다
   (HUD `더보기 ▼` · 던전 `자세히 ▾` 가 그 대체 경로다).
6. 정적 검사를 무시해야 하면 `mobile-ok: <이유>` 주석을 **룰 바로 위에** 달아라. 이유 없는 면제 금지.
7. ★ **CSS 템플릿 리터럴 안의 주석에 백틱을 쓰지 마라.** 리터럴이 그 자리에서 끊긴다.
   `node --check` 는 통과해 버려서(짝이 맞으면 파싱은 된다) 알아채기 어렵다 — 이번에 실제로 당했다.

### 13.6 회귀 — 게임 로직·밸런스 불변 확인

```
node tools/smoke.mjs               → ✅ 255건 전부 통과 (exit 0)
node tools/balance.mjs --only=quest → ✅ 통과 (전투 4,260회)
node tools/mobile.mjs              → ✅ 정적 검사 통과 (룰 741개 / 확인 117건)
```
랭크별 승률 **F 100 / E 74.1 / D 63.0 / C 62.2 / B 60.7 / A 57.4 / S 52.6** —
7차에 확정한 목표 대역(§10.2) 안이고, 이번 작업이 순수 표시 계층이었음을 뒷받침한다.

### 13.7 남은 것 / 다음 담당자에게

- **가로 화면(landscape)은 재지 않았다.** 800x360 같은 폰 가로는 `≤767px` 에 안 걸려
  PC 레이아웃이 뜨는데 세로 높이가 360px 뿐이다. 필요하면 `(orientation: landscape) and (max-height: 480px)`
  밴드를 따로 봐야 한다.
- **실기기 터치는 못 해 봤다.** 데스크톱 브라우저의 뷰포트 리사이즈로만 쟀다 —
  스크롤 관성·`100dvh`·iOS 주소창 축소는 실기기에서 다시 봐야 한다.
- **768~1024px 밴드의 글자 크기는 손대지 않았다.** 9~11px 라벨이 그대로다(PC 설계 유지).
  태블릿을 본격 지원할 거면 이 밴드의 글자도 올려야 한다.
- `document.hidden === true` 인 환경에서는 전투 캔버스가 그려지지 않는다 —
  **도트 퀄리티·전투 연출은 이번에도 눈으로 확인하지 못했다**(§6-1 그대로 열려 있다).
- 전투 프레임 성능(§9.5)은 10차에도 미측정.

## 14. 11차 세션 — 월드맵 라벨 겹침 (폰) 수정

플레이어 지적: **"지도 글자들이 겹쳐서 잘안보인다"** (폰 스크린샷 첨부).

### 14.1 원인 — 라벨 솎아내기가 도시에만 걸려 있었다

`worldmap.js` 에는 이미 좁은 화면용 솎아내기(`thin = narrowMap()`, 캔버스 폭 < 560)가 있었다.
그런데 **그 규칙을 도시 라벨만 따르고 있었다.** 지도에 글자를 뿌리는 곳은 셋인데:

| 라벨군 | 그리는 곳 | 좁은 화면 규칙 | 폰(316px)에서 그려지던 개수 |
|---|---|---|---|
| 도시 이름 + 거리 | `drawNodes` | ✅ 있었음 | 8~10 |
| **지역 이름 + 바이옴·등급** | `drawRegions` | ❌ **없었음** | **14** (지역 7 × 2줄) |
| **경로 소요 일수 뱃지** | `drawLinks` | ❌ **없었음** | **20+** |

즉 화면에 뜨던 글자 40여 개 중 도시 이름은 1/4뿐이었고, 나머지가 서로를 덮고 있었다.

두 번째 원인은 **라벨이 자리 경쟁을 하지 않는다**는 것. 전부 무조건 노드 바로 아래에 찍혔다.
축척 0.32에서는 이웃 도시 노드 간격이 30px인데 글자는 13px 고정이라 반드시 겹친다.

### 14.2 계측 도구 — `tools/maplabels.mjs`

브라우저 프리뷰 창이 안 떠 있으면 rAF·타이머가 멈춰 스크린샷으로 확인이 안 된다.
그래서 `worldmap.js` 의 배치 계산(px/py/scale/thin/폰트/후보 자리)을 그대로 옮긴
헤드리스 계측기를 만들었다. 라벨 사각형을 만들어 겹치는 쌍을 센다.

- 글자 폭은 추정한다(한글 1.0em / 그 외 0.55em). **실측 대조 완료** — 브라우저
  `measureText` 와 비교했더니 한글은 오차 0.0px(비율 1.000), 숫자만 2.7% 좁게 잡힌다.
- **현재 도시 × 선택 도시를 전수(54가지)로 돈다.** 한 자리만 재면 운으로 통과한다 —
  실제로 초기 수정안이 단일 위치에서는 PASS였는데 전수로는 7쌍이 남았다.
- 양방향 링크가 같은 뱃지를 두 번 그리는 건 겹침이 아니라 중복 draw 이므로 따로 센다.

### 14.3 고친 것

1. **지역 이름** — 좁은 화면에서 생략 (`drawRegions` 에 `if (narrowMap()) continue`).
   지역 구분은 색 얼룩으로 이미 되고, 자세한 건 도시를 누르면 나온다.
2. **경로 일수 뱃지** — 좁은 화면에서 생략. 같은 정보가 **도시 라벨 둘째 줄("3일")에 이미 있다.**
3. **라벨 자리 경쟁 도입** (`placeLabel` / `queueLabel` / `flushLabels`).
   - 라벨을 바로 그리지 않고 큐에 모았다가 **우선순위 순으로** 자리를 잡는다.
     `열린 던전(-1) > 현재 위치(0) > 고른 곳(1) > 가리킨 곳(2) > 이웃(3) > 나머지(4)`.
     도시와 던전은 그리는 순서(던전이 위)와 자리 잡는 순서가 달라서 큐가 필요했다.
   - 후보 자리 6개: 아래 → 위 → 우 → 좌 → 더 아래 → 더 위. 전부 막히면 그리지 않는다.
     **후보를 아래/위 2개만 뒀을 때는 전수 검사에서 7쌍이 남았다** — 좌우를 넣어야 0이 된다.
   - **캔버스 밖으로 나가는 자리는 후보에서 뺀다.** 예전에는 던전 라벨만 `d.y < MAP_H*0.88`
     로 아래/위를 뒤집어 잘림을 피하고 있었는데, 그 처리를 `placeLabel` 이 흡수하면서
     도시 라벨까지 한꺼번에 거른다(계측기도 `화면밖` 개수를 같이 센다).
   - 지역명·일수 뱃지도 그려지는 순서대로 자리를 **선점**한다(넓은 화면에서 도시 라벨이 피하도록).
   - `force`(현재 위치·고른 곳)도 빈자리부터 찾는다. 자리 검사를 통째로 건너뛰면
     "현재 위치"와 "고른 곳"이 서로 겹친다. 6개 후보가 다 막힌 경우에만 강행한다.
4. **전체 도시 목록 패널** (`allCityPanel`) — 좁은 화면 전용.
   라벨을 솎아내면 나머지 도시가 **이름 없는 점**이 된다. 이름으로 골라 갈 수 있는 길을 남겼다.
   `narrowMap()` 은 `layout()` 전에는 이전 값이라 DOM 은 항상 만들고 `layout()` 이 표시를 정한다.

### 14.4 측정 결과 (`node tools/maplabels.mjs`, 상황 54가지 전수)

| 폭 | 수정 전 겹침 합계 | 수정 후 | 최소 표시 라벨 |

자리 경쟁이 넓은 화면에도 적용되기 때문. 태블릿도 58→62로 늘었다(후보 자리를 6개로

### 14.5 실기 확인 (폰 360x800, 프리뷰)

```
                 왕의안식 · 2일 / 잿빛여울 · 3일 / 수렁폭포 · 3일
```


### 14.7 남은 것

- **PC(1280px) 실기 확인은 못 했다.** 프리뷰 창이 표시되지 않으면 rAF·setTimeout 이
  스로틀링돼 지도 탭 mount 가 안 끝난다(폰 폭에서는 한 번 잡혔다). 헤드리스 전수 검사는
  PC 폭에서 PASS 이고 PC 전용 분기는 `narrowMap()` 하나뿐이라 위험은 낮지만, 눈으로는 못 봤다.
- 라벨을 솎아내면 폰에서 이름이 뜨는 도시는 **현재 위치 + 이웃뿐**이다(위 실측 5곳).
  `allCityPanel` 로 길은 열어 뒀지만, 지도만 보고 먼 도시를 파악하는 건 여전히 안 된다.
  지도 확대/패닝을 넣을지는 판단이 필요하다.
- §13.7 의 남은 항목(가로 화면, 실기기 터치, 768~1024 밴드, 전투 프레임 성능)은 그대로다.

## 15. 11차 세션 (이어서) — 세로 전용 전장 + PWA + 배포 (검증)

> §14 와 **같은 11차 세션**이다. 플레이어 지적 두 가지를 더 처리했다:
> **"폰 세로에서 전투가 너무 작아 관전이 안 된다"** / **"홈 화면에 추가해도 브라우저 껍데기다"**.
> 두 에이전트가 구현했고 이 절은 **실측 검증**이 맡은 부분이다.
> **게임 로직·밸런스·데이터는 한 줄도 건드리지 않았다** (§15.6 회귀 — 승률이 §13.6 과 소수점까지 같다).
>
> 화면 방향은 **세로 고정**으로 확정됐다. 가로 레이아웃은 만들지 않는다.

### 15.1 무엇이 바뀌었나 — 세로 전용 전장

**엔진의 필드 좌표계(가로 100 x 세로 60)는 그대로다.** 바뀐 것은 "필드 → 화면" 매핑뿐이라
전투 결과는 영향을 받지 않는다.

| 층 | 바뀐 것 |
|---|---|
| `ui/battle.js stageSpec()` | 폰(≤767px)에서 캔버스 **논리 크기를 세로로 길게** 잡는다. 논리 폭은 "스프라이트가 화면에서 `PHONE_SPRITE_PX`(70) CSS px 로 보이도록" 역산하고, 논리 높이는 실제로 남는 세로 공간을 그 배율로 되돌려 잡는다. **PC 는 예전 그대로 1280x560 고정.** |
| `battle/renderer.js` | `H >= W * PORTRAIT_ASPECT(0.72)` 면 **세로 매핑**으로 전환. 가로는 진영 사이 빈 공간(필드 x 44~56)을 눌러 담고 남은 폭을 진영 띠에 전부 준다(조각별 선형, 단조 증가 유지). 세로는 유닛이 실제로 서는 구간(필드 y 8~52)을 캔버스 세로에 펼친다. |
| 오버레이 배율 `uiScale` | 캔버스가 CSS 로 축소되면 논리 12px 글자가 화면에서 5px 도 안 된다. 표시 폭을 보고 **오버레이(이름표·HP 바·숫자·HUD)만** 키운다. 스프라이트·진형은 안 건드린다. **PC 에서는 항상 1 로 clamp** 되므로 그림이 예전과 완전히 같다. |

폰에서는 홈 화면 아이콘으로 열고 → 배너가 뜨면 `새로고침`. 안 뜨면 이미 최신이다.

## 16. 11차 세션 (이어서) — 안드로이드 앱(TWA)으로 감싸기

플레이어 요구: **"홈화면에 빼둔거 삼성 게이밍허브에는 못넣나?"**

### 16.1 왜 PWA 로는 안 되나

삼성 게이밍 허브는 두 가지만 인식한다.

1. 앱 스토어에 **'게임' 카테고리로 등록된 앱** → 자동 추가
2. **설치된 앱** → 수동 추가 (내 게임 → ⋮ → 게임 추가)

홈 화면 PWA 바로가기는 **둘 다 아니다.** 플레이어도 "앱만 인식하는것같아" 로 확인해 줬다.
매니페스트의 `"categories": ["games"]` 는 **웹 앱 스토어 분류용**이라 안드로이드가 게임 판정에
쓰는 `android:appCategory` 와 무관하다 — 크롬이 둘을 이어 준다는 근거는 못 찾았다.

그래서 같은 사이트를 감싼 **TWA(Trusted Web Activity) APK** 를 만들었다.
프로젝트는 `C:\claude\merc-twa` — **웹 저장소 밖**이다.
`C:\claude\game` 루트는 Pages 가 그대로 공개하므로 키스토어·APK 가 그 안에 있으면 인터넷에 노출된다
(`.gitignore` 에 `*.keystore`/`*.apk`/`*.aab` 를 넣어 이중으로 막았다).

### 16.2 assetlinks.json 은 **오리진 루트에만** 놓을 수 있다 (여기서 한 번 틀렸다)

```
O  https://sryanius.github.io/.well-known/assetlinks.json
X  https://sryanius.github.io/merc-company/.well-known/assetlinks.json
```

게임은 프로젝트 페이지(`/merc-company/`) 아래에 있다. 처음에 거기 넣었는데 안드로이드는
**오리진 루트만** 본다. 검증 실패 = 앱 상단에 주소창이 남는다.
그래서 저장소를 하나 더 만들었다 — **`sryanius/sryanius.github.io`** (루트 페이지 + 검증 파일).

두 번째 함정: **GitHub Pages 는 Jekyll 이 기본이고, Jekyll 은 `.` 로 시작하는 디렉터리를 뺀다.**
`.nojekyll` 이 없으면 `.well-known` 이 404 다. 사용자 페이지 저장소에 넣어 해결했다.
참고로 **프로젝트 페이지(merc-company)에서는 `.nojekyll` 을 넣어도 닷폴더가 안 나갔다**(404 유지) —
어차피 안 쓰는 경로라 그 사본은 지웠다.

검증 확인은 눈이 아니라 구글 API 로 한다:
```bash
curl -s "https://digitalassetlinks.googleapis.com/v1/statements:list?source.web.site=https://sryanius.github.io&relation=delegate_permission/common.handle_all_urls"
```
`statements` 에 우리 패키지명·지문이 나오면 통과. **통과 확인함.**

### 16.4 툴체인 함정 (다음 사람이 반드시 다시 만난다)

- Bubblewrap 은 SDK 루트에 `tools/` 나 `bin/` 이 있어야 유효하다고 본다(`AndroidSdkTools.validatePath`).
  요즘 `cmdline-tools` 레이아웃엔 없다. → `android-sdk\bin` → `cmdline-tools\latest\bin` **정션** 생성.
- Bubblewrap 이 요구하는 build-tools 버전이 코드에 박혀 있다(현재 `36.1.0`). 다른 버전만 깔면 서명이 깨진다.
- **`bubblewrap update` 는 `AndroidManifest.xml` 을 덮어쓴다** → `android:appCategory="game"` 이 날아간다.

## 17. 12차 세션 — 무한의 탑 + 펫

플레이어 요청: 1~500층, 매달 1일 입장, 층당 골드, 자동 진행, 소탕(최고−100), 보상은 펫.
펫은 부대당 3마리, 공격/대신맞기/버프/회복.

### 17.1 착수 전에 코드베이스를 먼저 재 봤다 (그리고 설계가 바뀌었다)

병렬 정찰(8에이전트)로 붙일 자리를 먼저 그렸다. **요구사항 그대로 만들면 안 되는 것이 넷** 나왔다.

1. **500층은 그대로 만들면 실질 60층이다.** 난이도 축이 스칼라 `power` 하나뿐인데
   실측 해상도가 `4.70→100% / 5.20→36% / 5.90→0%` 로 의미 있는 밴드가 Δ0.35 뿐이다.
   → **체력 이월**을 두 번째 축으로 도입(플레이어 승인). 실측으로 효과 확인:
   풀세트가 400층을 만피로는 100% 이기는데 실제 등반은 378층에서 멈춘다.
2. **전투 화면으로는 자동 진행이 불가능하다.** 5차 세션에 플레이어가 요청한
   "클릭해야 넘어간다" 계약이 코드에 박혀 있고, `fastForward()` 에는 **12웨이브 하드 캡**이 있어
   탑을 웨이브로 만들면 13층에서 런 전체가 조용히 패배 처리된다.
   → 헤드리스 `simulate()` 루프 + 층별 요약 로그(플레이어 승인).
3. **펫을 진형에 넣으면 진형 12개가 죽는다.** `quest.js:701` `f.slots.length === 7` 검사에 걸려
   골드로 산 진형이 전부 기본 좌표·무보정이 된다(예외도 로그도 없다).
   → 진형 밖 고정 열(`PET_SLOTS`, x=0.96)에 세우고 `slotIndex` 를 안 넘긴다.
4. **"대신 맞기"는 엔진에 자리가 없었다.** `applyDamage(srcUid, tgt, …)` 의 `tgt` 는 고정이고
   가로챌 수 있는 건 죽음(`lethal`)뿐이었다. → 재대상 훅을 새로 열었다.

정찰이 잡아낸 다른 함정들(전부 반영):
`squadUnitDefs` 는 **프로덕션 호출자가 0** (거기 배선하면 도구는 초록불인데 게임엔 안 나온다) /
`replaceState` 는 세이브 값이 무조건 이겨서 `pets:null` 이 그대로 박힌다 /
`normalizeDungeons` 가 항목을 2키로 재구성해 탑 필드를 버린다 /
달력에 `dayOfMonth` 가 없어 `dayOfWeek===1` 만 보면 한 달에 4번 참 /
`advanceDays` 에 월 경계 훅이 없어 플래그를 저장하면 리셋이 안 된다 /
드랍에 `globalRng` 를 쓰면 `load()` 가 시드를 되감아 새로고침 리롤이 가능해진다 /
`newGame` 이 `createSquad` 를 안 부르고 부대 리터럴을 복제해 둬서 한쪽만 고치면 새 게임에만 버그.

### 17.2 확정 수치

| 항목 | 값 | 근거 |
|---|---|---|
| 층 비용 | 층수 × 2 (누적 250,500G) | 플레이어 결정 (공식 5는 누적 62만이라 의도와 안 맞았다) |

### 17.5 브라우저 실측

기존 세이브(35명·5부대)가 마이그레이션되고 콘솔 에러 0.
탑 화면·펫 화면 렌더 확인, 펫 배치 왕복 확인, 등반 1회 26ms.

작업 중 잡은 UI 버그 하나: **`app.js` 의 `refresh()` 는 다시 그리기 전에 `dispose()` 를 부른다**

→ `dispose()` 에서 `picking` 을 안 지운다. **다른 화면을 만들 때도 같은 함정이 있다.**

### 17.6 남은 것

- **1~100층이 사실상 평평하다.** `POWER_CURVE 1.85` 라 앞구간 배율 변화가 거의 없다
  (1층 2.70 / 100층 2.88). 소탕 대상 구간이라 의도한 것이지만, 저레벨 부대에게는
  1층과 50층이 같은 벽이다. 체감 진행을 원하면 앞구간에 별도 곡선이 필요하다.
- **탑은 월드맵 노드가 아니다.** 도시 화면의 달력 안내 옆에 넣었다
  (`ui/city.js towerRow`). 월드맵 캔버스는 라벨 배치를 막 고친 참이라 건드리지 않았다.
- **펫 스프라이트는 이족 인간형이다.** 리그가 32×40 이족 고정이라 4족·비행이 안 된다
  (수인·정령 계열로 표현했다). 진짜 동물형을 원하면 `composeFrame`/`JOINTS`/`POSES` 에
  새 리그를 추가해야 하고, 그 순간 `tools/portrait.mjs` 의 겹침 계산과 파츠 검증이 같이 깨진다.
- **적 펫은 아군 펫과 다른 취급이다.** 적으로 설 때는 `pet:true` 를 **안** 붙인다
  (붙이면 엔진이 승패에서 빼서 안 잡아도 이긴다). 대신 수호 능력도 안 쓴다.
- 펫 도감·펫 강화 같은 성장 요소는 없다. 등급과 종이 성능의 전부다.

## 18. 13차 세션 — 전투 로그 색 / 전장 배경 / **황금 나락**(골드 던전)

플레이어 지적 3건: (1) 웨이브 정리 말고는 로그가 다 하얗다, (2) "봉인된 석실 조사"인데
배경이 들판이다, (3) 의뢰만으로는 유지비를 못 낸다 — 주 1회 골드 던전을 달라.

> ⚠️ **§17 이후 이 문서에 안 적힌 작업이 여럿 있다** (탑 UI 보완 · 정원 70 · 던전 웨이브 연속 ·
> 장비 자동판매/일괄판매/용병별 보기 · 용병 이름 변경 · 진행도 재조정 · 튜토리얼 ·
> 세이브 암호화 · 도시 화면 접기). 코드 주석에는 근거가 남아 있지만 여기 요약은 비어 있다.

### 18.1 로그 색이 안 먹은 진짜 이유

색 입힌 `pushLog(text, kind, mark)` 와 CSS 10종을 `ui/battle.js` 에 넣어 뒀는데도 화면은 하얬다.
**로그 문구를 만드는 쪽이 거기가 아니었다.**

```js
// ui/battle.js — 렌더러가 붙으면 자기 쪽 로그를 통째로 끈다
if (typeof S.renderer.onLog === 'function') {
  S.externalLog = true;
  S.renderer.onLog((text) => pushLog(text, 'ally'));   // ← 종류가 'ally' 하나로 고정
}
```

`battle/renderer.js` 의 `log(text)` 는 **문자열 하나만** 보냈고, 받는 쪽이 전부 `ally`(흰색)로
칠했다. "웨이브 정리"만 색이 있었던 건 그 줄만 `externalLog` 밖에서 직접 찍히기 때문이다.

→ 렌더러의 `log(text, kind, mark)` 로 넓히고 이벤트별로 종류를 실었다
(피해=시전자 진영 / 치명타=`«치명타 N»` + `crit` / 회피 `miss` / 회복 `heal` /
기절·디버프 `debuff` / 사망 `down`·`downfoe` / 종료 `win`·`lose` / 스킬명 `«…»` + `skill`).
`bt-log-buff/debuff`, `bt-mk-skill/stun` CSS 를 새로 넣었다.

**실측(실제 의뢰 전투 1판, DOM 직접 확인):** 줄 클래스 8종 · 강조 3종이 붙는다.
```
bt-log-wave 1 / ally 36 / enemy 22 / debuff 2 / miss 7 / heal 3 / downfoe 3 / win 1
bt-mk-crit → "치명타 133"   bt-mk-skill → "관통 찌르기"   bt-mk-stun → "기절"
```

> 미리보기 창이 안 떠 있으면 rAF 가 멈춰 전투가 진행되지 않는다. `requestAnimationFrame` 을
> 큐로 바꿔치기해 프레임을 손으로 돌려야 로그가 나온다. 앞선 확인이 `bt-log-wave` 하나만
> 보고 통과했던 게 이 함정 때문이다.

### 18.2 전장 배경 — `scene` 을 `biome` 에서 갈랐다

의뢰의 `biome` 은 **도시 지형**이라 배경도 적 풀도 그걸 따랐다. 그래서 "…봉인된 석실 조사"인데
들판이 깔렸다. `biome` 을 바꾸면 `enemiesFor(biome, tier)` 가 적 풀을 바꿔 난이도표가 통째로
어긋나므로, **배경 전용 필드 `scene`** 을 새로 뒀다.

- `SCENE_WORD` (quest.js): 고분 · 봉인된 석실 · 땅굴 · 소굴 → `cave`. 나머지는 도시 지형 그대로
  ('무너진 제단'이나 '야영지'는 바깥이 맞다).
- `questBattleDefs` 와 `ui/battle.js` 가 `quest.scene || quest.biome` 을 쓴다 (옛 세이브 호환).
- 엔진은 `biome` 을 아예 안 읽는다 → **밸런스 영향 0**. 실측: 40일치 의뢰 중 35건이 `cave` 로 바뀜.

### 18.3 황금 나락 — 주 1회 골드 던전

| 항목 | 값 | 근거 |
|---|---|---|
| 입장 | **주당 1회, 요일 무관** | 탑처럼 날짜를 고정하면 그날 부대가 원정 중일 때 한 주치 임금 재원이 날아간다 |
| 보상 | 심층 n 당 `40G × n`, 10심층마다 금고 3배 | 아래 역산 |
| 비용 | 없음 | 탑이 골드 소모, 여기는 골드 공급 |
| 소탕 | 없음 | 층마다 **버는** 구조라 건너뛰면 그만큼 못 번다 |
| 드랍 | 골드만 (장비·펫·경험치 없음) | 플레이어 요구 |
| 난이도 | 배율 `1.60 × 1.0184^(n-1)` (지수) · 적 레벨 `28 + 1.2n` (80 클램프) · 적 3~7기 | 아래 실측 |
| 회복 지점 | 20심층마다 | 탑과 같은 이유 |
| 해금 | 최고 레벨 35 | 임금이 버거워지기 시작하는 지점 |
| 진입 | **도시 화면** (월드맵 노드 아님) | 임금 재원이라 "그 도시까지 가야 한다"가 되면 안 된다 |

**설계의 출발점은 지출 실측이다.** 주간 필요 골드 = 임금 7일 + 탑 비용 ÷ 4주:

```
정원 21 · Lv55 B · 4차   임금 14,994 + 탑 ~5,000  =  ~20,000G
정원 35 · Lv80 A · 4차   임금 61,005 + 탑 31,313  =   92,318G
정원 70 · Lv80 A · 4차   임금 76,258 + 탑 31,313  =  107,571G
정원 70 · Lv80 S · 4차   임금119,742 + 탑 31,313  =  151,055G
```

누적 보상이 깊이의 제곱으로 늘도록(`40G × n`) 잡고 계수를 역산했다.
**실측 (`node tools/abyss.mjs`, 잠수 5회 평균):**

```
구성                     도달심층    주간 수입    대응 필요치 대비
Lv30 2차 · 상점템           17.8       7,496G     (초반은 임금도 적다)
Lv55 3차 · 상점템           36.2      31,736G     20,000G 의 1.59배
Lv70 3차 · 상점템           42.4      44,264G
Lv80 4차 · 상점템           54.2      71,840G     92,318G 의 0.78배
Lv80 4차 · 풀세트           79.2     153,520G    151,055G 의 1.02배  ← 요구사항 지점
〃 + 저급/중급펫            80.4     157,344G
```

즉 **풀세트를 갖춘 최종 부대가 가장 비싼 정원(70명 Lv80 S)의 주간 지출을 딱 맞춘다.**
상점템 단계에서는 8할이라 의뢰 수입이 아직 필요하다 — 그게 세트를 모을 이유가 된다.

구조는 탑을 그대로 본떴다: 합성 의뢰 → `questBattleDefs`(진형·장비·세트효과·펫이 한 경로로
실린다) / 헤드리스 시뮬 / 심층별 독립 RNG(`load()` 시드 되감기로 리롤 못 하게) /
체력 이월 + 쉼터. **바닥(최고 심층)이 없다** — 배율이 지수라 어디선가 반드시 막힌다.
벌이의 상한은 층수가 아니라 부대의 힘이어야 하기 때문이다.

### 18.4 그러다 잡은 버그 — 쓰러진 단원이 두 층 뒤에 만피로 돌아왔다 (**탑에도 있었다**)

`carry[uid] = 0` 이 "이 사람은 쓰러졌다"는 표시인데, 편성 함수가 0 인 사람을 `cfg.allies` 에서
빼 버린다. 다음 층의 `carry` 는 그 `cfg.allies` 를 돌며 만들어지므로 **0 이 한 층만 살고 사라졌다.**
로그에는 "회복 지점까지 못 나온다"고 찍히는데 실제로는 두 층 뒤에 만피로 복귀했다
(같은 사람이 3·6·8심층에서 세 번 쓰러지는 로그로 발각).

→ `runFloor`/`runDepth` 에서 앞선 0 을 먼저 옮겨 담는다.

**탑이 실제로 어려워졌다.** 재측정 결과 저급펫 완주율이 25% → 0% 로 떨어져 §17.2 의 목표
("풀셋 + 저등급 펫이 어느 정도 있어야 간신히")가 깨졌다 →
`POWER_MAX` **7.20 → 7.00**. 재측정: 풀세트 468층·0% / 저급펫 483층·17% / 중급 491 / 고급 500·100%.
목표 판정 6종 전부 통과.

### 18.5 부수적으로 고친 것 — `wm-*` CSS 가 월드맵에만 있었다

`.wm-ev` / `.wm-nb` / `.btn.sm.wm-go` 는 `worldmap.js` 가 **화면 진입 때 주입**하는 스타일이었다.
탑·나락 화면이 이 클래스를 쓰는데 둘 다 도시에서 바로 들어올 수 있어서,
월드맵을 한 번도 안 열면 스타일이 통째로 빠졌다 → `css/style.css` 로 옮겼다.

  안 맞고, 라벨 배치를 막 고친 캔버스를 또 건드리고 싶지 않았다).

## 19. 14차 세션 — 클라우드 세이브 · 구글 로그인 · 랭킹 (Supabase)

플레이어 요청의 출발점: **"세이브 조작하는 놈이 있어서 DB로 바꿔야겠는데"** →
논의 끝에 랭킹까지 붙였다.

### 19.1 착수 전에 정한 것 — 세이브와 랭킹은 다른 물건이다

**디비로 옮겨도 조작은 안 막힌다.** 게임이 브라우저에서 다 계산하므로 클라이언트가
"골드 999999로 저장해줘"라고 보내면 서버는 그대로 저장한다. 막히는 건 파일 편집뿐이다.
이걸 먼저 못 박고 설계를 갈랐다:

| | 검증 | 쓰는 주체 | 빈도 |
|---|---|---|---|
| **세이브** `saves` | **안 한다** | 클라이언트 (RLS 로 본인 것만) | `save()` 마다 (20초 디바운스) |
| **랭킹** `scores` | **한다** | **Edge Function 만** (INSERT/UPDATE 정책 자체가 없다) | 기록 갱신 때만 |

세이브를 조작해 봐야 본인 게임만 이상해진다. 거기에 검증을 걸면 밸런스 패치 때마다
정상 플레이어가 세이브를 잃는다. 그리고 이 분리 덕에 **서버 함수가 거의 안 불린다** —
탑은 월 1회, 나락은 주 1회로 게임이 강제하므로 기록이 오르는 일 자체가 드물다.

> **정직하게: 이건 "조작 방지"가 아니라 "개연성 검사"다.** 그렇게 광고하면 안 된다.

### 19.2 supabase-js 를 안 쓴다 (`fetch` 만)

셋 다 실제 위험이라 골랐다:
1. **의존성 0 · 빌드 없음**이 이 프로젝트의 불변식이다.
2. `sw.js` 는 교차 출처를 캐시하지 않는다 — CDN 이 안 뜨면 **오프라인에서 게임이 아예
   부팅되지 않는다.** TWA 앱·iOS PWA 에서 그건 곧 앱 장애다.
3. 필요한 엔드포인트가 4개뿐이다. 250줄이면 되는 걸 120KB 로 바꿀 이유가 없다.

PKCE 도 직접 구현했다(브라우저 crypto 20줄). implicit 은 토큰이 URL 조각으로 돌아와
방문 기록에 남는다.

### 19.3 익명 로그인 → 구글 로그인으로 갈아탄 이유

처음엔 익명 로그인으로 만들었다(화면 한 번 안 띄우고 랭킹 참여). 그런데
**브라우저 저장소가 지워지면 계정이 사라진다** — iOS PWA 는 며칠 안 쓰면 실제로 정리한다.
복구 코드도 "코드를 잃으면 끝"이라 문제를 미룰 뿐이었다.

이메일+비밀번호는 설정이 제일 쉽지만 **Supabase 내장 메일 발송이 시간당 몇 통 수준이고
공식적으로 테스트용**이라 비밀번호 찾기가 사실상 안 된다. 구글은 메일 발송이 아예 필요 없고
복구를 구글이 책임진다.

갈아타면서 걸린 함정: **익명 시절 세션이 저장소에 남아 `signedIn()` 이 참이라
구글 로그인 화면이 영영 안 떴다.** 이메일 유무로 갈라 옛 세션을 버린다.
계정 전환에는 `prompt=select_account` 가 **반드시** 필요하다 — 구글이 세션을 기억해서
그냥 다시 로그인하면 묻지도 않고 같은 계정으로 들어간다.

### 19.4 검증 규칙은 한 벌만 (`src/game/rules.js`)

규칙을 SQL 로 옮겨 적으면 손으로 베낀 두 번째 사본이 생기고, 밸런스를 고치는 날
정상 플레이어가 전원 거절당한다. 그래서 게임 상수를 그대로 읽는 순수 모듈 하나만 둔다.

**가장 강한 무기는 입장 제한이다.** 나락은 주 1회, 탑은 월 1회로 코드가 강제하므로
기록이 올랐다면 `lastRunDay` 가 새 주(달)로 넘어가 있어야 한다 — 날짜 산술이 아니라
게임 규칙 그대로라 오탐이 원리상 없다.

> 처음엔 "지난 제출 이후 며칠 지났나"로 셌는데, 그러면 같은 날 제출 두 번에 기록이
> 40 → 200 으로 뛰어도 통과했다(계측기가 잡았다). 반대로 날짜만 조이면
> "같은 날 두 번 제출"이라는 정상 동작이 막힌다.

서버로 가져가려니 `rules.js` 가 `merc.js`(import 6개)·`state.js`(14개)를 물고 있어
**게임 전체가 딸려 왔다.** → `data/limits.js`(**import 0개**)로 상수를 옮기고 원래 자리에서는
다시 내보낸다. 주의: `export {} from` 은 지역 바인딩을 안 만든다 — `state.js` 는 내부에서도
쓰므로 import 와 export 를 **둘 다** 해야 한다.

복사본은 반드시 썩으므로 `tools/syncshared.mjs` 가 FNV 해시를 기록하고 스모크가 검사한다.
실제로 규칙을 고쳤을 때 드리프트 검사가 걸렸다(설계대로).

### 19.5 적대적 리뷰 — 데이터 손실 버그 9건 (15에이전트)

전부 재현이 붙어 있었다. 특히 **하나는 클라우드와 무관한, 전날 배포한 버그**였다:

**암호 관문에 걸린 옛 세이브가 새로고침 한 번에 사라졌다.**
`load()` 가 관문에서 `newGame()` 을 부르면 seed 가 채워져 `started()` 가 참이 되고,
`app.js` 가 boot() 에서 **load() 보다 먼저** 걸어 둔 `beforeunload → save()` 가
암호 모달 위에서 F5 한 번에 1일차 새 게임을 덮었다. 게다가 `sealMark` 까지 찍혀
**다음 부팅엔 관문조차 안 뜬다** — 사라진 줄도 모르게 된다.
→ `replaceState(defaultState())` 로 "시작 전 빈 상태"를 만든다.
   ★ "newGame() 을 그냥 지우기"로는 부족했다 — `load()` 두 번째 호출에는 앞 게임이 남아 있다.

나머지 중 무거운 것:
- **새 게임(다른 seed)이 서버의 옛 판을 조용히 덮었다.** 트리거는 seed 가 다르면 rev 검사를
  건너뛴다(아카이브 분기). `saves_archive` 를 읽는 코드가 0줄이라 꺼낼 수도 없었다.
- **`rev` 는 저장 횟수지 진행도가 아니다.** 5일차에서 천 번 저장한 쪽이 200일차에서 쉰 번
  저장한 쪽을 이긴다 → 화면이 "서버가 더 최신"이라 **거짓말하며** 200일차를 덮으라고 권했다.
  `divergent` 를 따로 알리고, 문구·기본 버튼을 **일수**로 정한다. 갈렸으면 어느 쪽도 강조하지 않는다.
- **`local-newer` 면 묻지도 않고 덮었다** (부팅 경로에서 조용히).
- **모달이 "되돌릴 수 있다"고 적는데 되돌리는 코드가 0줄이었다.**
- **`refresh()` 가 네트워크 실패에도 세션을 버렸다** — 익명 시절엔 그게 계정 영구 삭제였다.
- **지수 백오프가 장식이었다** — `nextAt` 을 아무도 안 읽었다. 고치는 중에 내가 `nextAt: 0`
  구멍을 또 냈고, 예약을 `scheduleRetry()` 하나로 모아 같은 실수 자리를 없앴다.

- `npx supabase db query --linked -f <파일>` 로 원격 SQL 을 직접 돌릴 수 있다

## 20. 등급 격차 실측 (`node tools/gradegap.mjs`)

"F 한 부대와 S 한 부대가 얼마나 차이 나나"에 대한 답. 같은 3차 클래스 7인 · Lv60 · 장비 없음.

```
등급   체력     공격    방어   전투력    일임금
 F    36012    2113    993    17908      133G
 C    48942    2871   1349    24230      406G
 S    71563    4197   1973    35249     1491G

F → S  스탯 1.99배 · 전투력 1.97배 · 임금 11.2배 · 고용비 66.7배
```

**맞대결은 한 칸만 벌어져도 전멸이다** (각 12판):
```
F vs F  50%      F vs E  0%      E vs D  0%      D vs C  0%
C vs B   0%      B vs A  0%      A vs S  0%
```
스탯 12% 차이가 승률 0% 로 나오는 건 공·방·체가 **동시에** 곱해지기 때문이다
(Lanchester 식 소모전). 표의 배율만 보면 이 크기를 못 읽는다.

**등급은 레벨을 압도한다:**
```
등급 한 칸  ×1.121        레벨 10개  ×1.137
→ 등급 한 칸 ≈ 레벨 9개 · F→S 는 레벨 53개어치
→ F Lv80 은 S Lv60 의 65% — 레벨 상한(80)까지 올려도 못 따라잡는다 (0/12)
```

**실제 진행 차이** (황금 나락 도달, 잠수 3회 평균):
```
F 19.0심층  ·  C 24.7심층  ·  S 33.0심층
```

### 이 수치를 어떻게 읽을 것인가

- **S 가 고용비 67배·임금 11배인 것은 성능(2배)에 비해 비싸 보이지만**, 맞대결이 0% 로
  갈리는 걸 보면 "2배"가 실제 체감의 하한이다. 가격은 성능이 아니라 **결과**를 따라간다.
- **레벨로 등급을 못 메운다**는 것이 이 게임 성장 설계의 핵심이다. 시간(레벨)으로는
  한계가 있고 등급은 특화 도시 순회로만 얻으므로, "어디로 갈 것인가"가 "얼마나 오래
  키울 것인가"보다 중요해진다. 명물 색인을 월드맵에 넣은 이유가 이것이다.
- 등급 격차가 이렇게 가파른 것이 **의도인지 확인이 필요하다.** 한 칸 차이가 0% 라는 건
  "B 부대로 A 상대를 만나면 무조건 진다"는 뜻이고, 의뢰 난이도 표시(색)가 이 낭떠러지를
  플레이어에게 제대로 전달하고 있는지는 따로 재 본 적이 없다.

전달하는지** 따로 쟀다. 색은 `ui/quests.js dangerLevelByPower` 가 **전투력 비율 하나**로 정한다.

아군 A등급 Lv80 기준, 적 등급만 바꿔가며 (각 20판):
```
적    전투력비  색            실제
F     1.71배   식은 죽 먹기   100%   ✓
E     1.52배   여유          100%   (색은 '유리' — 실제는 확정승)
D     1.38배   여유          100%
C     1.26배   여유          100%
B     1.13배   적정          100%   ✗ '반반' 인데 확정승
A     1.00배   적정           88%   ✗
S     0.87배   위험            0%   (색은 '불리' — 실제는 확정패)
```

전환점을 촘촘히 재면:
```
전투력비 1.05 → 100%      1.00 → 50%      0.88 → 0%
승률 50% 는 비율 0.88~1.00 사이 · 폭 0.12
'적정' 구간은 0.92~1.22 · 폭 0.30 → **10배 넓다**
```

### 무엇이 문제인가

1. **'적정'(반반)이 반반이 아니다.** 실제로는 비율 1.0 을 경계로 확정승/확정패가 갈린다.
   구간 폭이 실제 전환 폭의 10배라, 같은 '적정' 안에서 100% 와 0% 가 함께 산다.
2. **색이 원인을 구분하지 못한다.** 같은 비율이라도 등급에서 온 것과 레벨에서 온 것의
   결과가 다른데, 비율 하나만 보므로 알 수 없다.
3. **아군 쪽에 구조적 이점이 있다.** 완전히 같은 부대끼리(A vs A, 비율 1.00)가 88% 다.
   50% 여야 정상이다 — 선공·진형 배치 중 무엇 때문인지는 **아직 안 밝혔다.**

### 손대기 전에 정해야 할 것

경계값만 좁히면(예: 적정 0.97~1.05) 색은 정확해지지만 **대부분의 의뢰가 '식은 죽 먹기'
아니면 '무모'** 로 뜬다. 그게 실제 게임 상태이므로 거짓말은 아니지만, 색으로 고르는
재미는 사라진다. 둘 중 하나다:

- **색을 실제에 맞춘다** — 정직하지만 중간 구간이 사라진다.
- **전투 자체의 낭떠러지를 완만하게 만든다** — 방어/회피의 수확체감을 넣는 등.
  이쪽이 근본이지만 밸런스 전체를 다시 재야 한다(`balance.mjs` · `dungeon.mjs` · `tower.mjs` ·
  `abyss.mjs` 가 전부 지금 곡선 위에 서 있다).

**아직 아무것도 안 고쳤다.** 어느 쪽을 택할지는 제작자 결정이다.

### ★ 계측 도구들의 기준 등급이 서로 다르다 (확인 필요)

이번에 조사하다 발견했다:
```
tools/tower.mjs      Lv80 A      ← 플레이어가 의도한 기준
tools/abyss.mjs      Lv80 A
tools/dungeon.mjs    Lv80 **B**  ← 다르다
tools/setspecial.mjs Lv80 **B**  ← 다르다
tools/balance.mjs    레벨별 D~A 혼합
tools/earlygame.mjs  gradeRoll (무작위 — 시뮬이라 적절)
```
등급 한 칸이 승률 0% 로 갈리는 게임에서 **B 기준과 A 기준은 전혀 다른 난이도**다.

→ **재측정하고 고쳤다. §22 참고.**

## 22. 던전 난이도를 A등급 기준으로 다시 잡았다

제작자 결정: **"Lv80 · 평균 A등급으로 플레이했을 때 의도한 결과가 나와야 한다."**
그런데 도구마다 기준이 달랐다 — `tower`/`abyss` 는 A, `dungeon`/`setspecial` 은 B.

### 실측 — B 곡선을 A 부대로 재니 목표 두 개가 깨져 있었다

```
                    grade B(옛 기준)   grade A(실제 기준)   목표
세트 0개 평균 도달        1.6            3.2            ≤ 2.5   ✗
풀세트 10웨 완주율        25%            73%            15~50%  ✗
```
A 부대에게 던전 후반이 사실상 풀려 있었다 — 완주율이 의도(30%)의 두 배가 넘는다.

### 고친 값

```
옛: [2.68, 2.70, 2.72, 2.74, 2.76, 2.80, 2.90, 3.05, 3.30, 6.00]   (grade B 기준)
새: [2.92, 2.94, 2.96, 2.99, 3.01, 3.05, 3.16, 3.32, 3.60, 6.35]   (grade A 기준)
     └───────────── 1~9웨 × 1.09 ─────────────┘        └ 벽 ┘
```

**10웨 감도(A 기준)** — 한 칸이 매우 가파르다:
```
6.10 → 70%    6.25 → 47%    6.30 → 35%    6.35 → 29%    6.58 → 0%
```

**시행착오**: 처음엔 A/B 스탯비(1.136)를 그대로 곱했는데(1~9웨 ×1.136, 10웨 6.58)
**장신구 게이트가 5% 로 막히고 완주율이 0%** 가 됐다. 초반 웨이브는 게이트가 걸려 있어
스탯비만큼 올리면 안 된다 — ×1.09 가 게이트를 살리는 상한이었다.

### 결과 (A 기준 · 모든 목표 통과)

```
장비        평균도달   10웨 완주
전설10        1.6        0%
세트3         5.5        0%
세트5         7.6        0%
세트7         8.7        0%
세트8         8.7        0%
풀세트        9.3       29%   ← 목표 30%
```
게이트 둘 다 살아 있다 (방어구5 → 6웨 도달 / 방어구+장신구8 → 9웨 도달).

### 같이 한 것

- `tools/dungeon.mjs` · `tools/setspecial.mjs` 의 **기본 등급을 B → A** 로 바꿨다.
  이제 모든 난이도 도구가 같은 잣대(Lv80 A)를 쓴다.
- `setspecial` 은 **난이도가 아니라 고유효과 구현이 맞는지** 재는 도구라 등급 영향이
  없었다(B/A 동일 통과). 기준만 맞춰 두었다.
- 회귀: smoke 294 · setspecial · balance(quest) · tower · abyss 전부 통과.
  나락·탑은 원래 A 기준이라 수치가 안 변했다.

## 23. 용병단 개명 (5만 골드)

**HUD의 용병단 이름을 누르면** 개명창이 뜬다 (`src/ui/app.js` `doRenameCompany`, `RENAME_COST = 50_000`).

### 왜 버튼을 안 달았나
헤더 버튼은 이미 줄이는 방향으로 정리한 참이다. "이름을 바꾸려면 이름을 누른다" 가
버튼을 하나 더 다는 것보다 자연스럽고, 용병 상세의 이름 옆 수정 아이콘과도 같은 결이다.
`.hud-brand` 에는 원래 클릭 핸들러가 없었다 — HUD 접기/펴기는 «더보기 ▼» 쪽이다.

### 왜 공짜가 아닌가
이름은 **순위표에 그대로 뜬다.** 공짜면 남을 사칭하거나, 기록을 세운 뒤 이름만 바꿔
치는 게 가능하다. 5만 골드는 초반엔 부담이고 후반엔 부담이 아닌 값 — 막자는 게 아니라
한 번 생각하고 바꾸게 하려는 것이다.

### 지킨 것
- **골드 검사를 두 번 한다.** 창을 연 채로 다른 화면에서 골드를 쓸 수 있으므로,
  바꾸기 직전에 다시 본다. 모자라면 부족분을 숫자로 알려 준다.
- 빈 이름 · 지금과 같은 이름이면 창을 닫지 않고 그 자리에서 사유를 띄운다.
- 이름 정리는 새 게임과 **같은 `cleanName` + `NAME_MAX`(20자)** 를 쓴다.
  (`'  검은  늑대  '` → `'검은 늑대'`)
- 성공하면 순위표 이름도 따라가도록 `Cloud.submitScore({ force: true })` 를 한 번 쏜다.
  기록이 안 올랐으니 평소 경로로는 제출이 안 나간다. 실패해도 조용히 넘어간다 —
  이름은 이미 바뀌었고 다음 기록 때 어차피 따라간다.

이름은 순수 표시용이다. 세이브·전투·랭킹의 키는 전부 `uid` / `user_id` 라 바꿔도 안전하다.

### 실측 (브라우저)
| 경우 | 결과 |
|---|---|
| 빈 이름 | 창 유지 · 골드 그대로 |
| 지금과 같은 이름 | 창 유지 · 골드 그대로 |
| 정상 (90,000G) | 40,000G · HUD 즉시 갱신 |
| 골드 부족 (40,000G) | 「골드가 10,000G 모자랍니다」 · 창 유지 |

※ 튜토리얼이 떠 있는 동안은 덮개에 막혀 눌리지 않는다. 그 시점엔 5만 골드가 없으므로 둔다.

## 24. 전투 절벽 조사 — 그리고 난이도 색을 예보로 바꿨다

### 24.1 절벽은 실재한다 (거울전, 지점당 300판)

| 전투력비 | 승률 |
|---|---|
| 1.041 | 100% |
| 1.010 | 82% |
| **1.000** | **51%** |
| 0.990 | 7.7% |
| 0.953 | 0% |

10%→90% 전이 폭 = **0.025**. 그런데 「적정」 밴드 하나가 **0.30** — 전이 폭의 **12배**다.
한 색 안에 확실한 승리와 확실한 패배가 같이 사는 게 당연했다.

### 24.2 더 큰 문제는 전투가 아니라 **예측기**였다

실제 의뢰 10건에서 "승률 50% 가 되는 전투력비"를 재 봤다:

```
1웨이브 의뢰   0.771 ~ 0.797
2웨이브 의뢰   0.633 ~ 0.725
→ 50% 지점이 0.633 ~ 0.873 에 흩어진다 (폭 0.240)
```

**절벽 폭(0.025)보다 위치가 9.6배 더 흔들린다.** 게다가 50% 지점이 전부 1.0 아래 —
화면이 「위험」(0.70~0.92)이라 쓰던 구간이 실제로는 확실한 승리였다.
`questFoePower` 의 웨이브당 +18% 가산이 다웨이브 의뢰를 과대평가한 탓이다.
**경계를 어떻게 옮겨도 맞힐 수 없다**는 뜻이라, 경계 대신 **자를 바꿨다.**

### 24.3 정정 — "같은 부대끼리 88%" 는 틀렸다

| 표본 | 산술수열 시드 | 잘 섞은 시드 |
|---|---|---|
| n=20 | 80.0% | 30.0% |
| n=200 | 54.5% | 50.0% |
| **n=2000** | **50.8%** | **50.0%** |

거울전은 정확히 공평하다. 원인은 `tools/dangercheck.mjs` 가 n=20 에 시드를
`9001+i*7919` **산술수열**로 쓴 것이었다. xorshift 와 상관이 생긴다.
→ 도구를 다시 썼다. 표본을 늘리고, 시드는 splitmix32 로 섞고, 판정(exit code)을 넣었다.

### 24.4 무엇을 만들었나 — `src/game/forecast.js`

카드의 색을 전투력 비율이 아니라 **실제 전투를 돌려 본 승률**로 정한다.

- **전투 코드는 한 줄도 안 건드렸다.** 확인: `balance.mjs` 출력이 변경 전후로 **완전히 동일**하다.
  기존 밸런스 곡선(WAVE_POWER · 탑 · 나락 · 세트)은 전부 그대로 유효하다. DATA_VERSION 불필요.
- **전역 rng 를 안 민다.** 전투 경로(`questBattleDefs` → `createBattle`)는 전부 자기 시드로만 돈다.
  안 그랬으면 화면을 보기만 해도 전리품·부상 판정이 달라졌을 것이다. smoke 가 이걸 검사한다
  (`rng.s` 를 고정하고 예보 전후 스트림을 대조 — 일부러 1칸 밀면 검사가 잡는 걸 확인했다).
- **웨이브 인계 규칙은 한 벌**이다. `WAVE_HEAL` · `applyWaveCarry` · `readWaveCarry` 를
  `game/quest.js` 로 올리고 `ui/battle.js` 와 예보가 같이 쓴다.
  smoke 가 `ui/battle.js` 에 사본이 생기는 걸 막는다.
- **밴드 경계도 한 벌**이다 (`forecast.js BANDS`). 도구가 손으로 베껴 적던 걸 없앴다.

### 24.5 표본 수 — 갈릴 때만 늘린다

기본 5판. 갈리면(만장일치가 아니면) 11판까지 더 굴린다.
실측 175건 중 174건이 만장일치라 추가 비용은 거의 없고, 정밀도가 필요한 건 갈린 판뿐이다.
(재정밀 도입 전에는 참승률 6.7% 인 의뢰가 2/5 로 「적정」에 뜨는 사고가 1건 있었다.)

### 24.6 화면에 붙이기

의뢰 한 건 예보가 3ms(쉬운 판)~43ms(박빙). 목록 16건이면 렌더를 막는다.
→ **표본 한 판씩** 쪼개 10ms 예산 안에서 돌리고, 끝나면 **그 카드만** 갈아 끼운다
(전체 재렌더는 스크롤·펼침을 잃는다). 재는 동안은 「재는 중」.

캐시 키 = 의뢰 + 부대 + **부대 지문**(인원·레벨·등급·장비·펫·진형·부상).
지문이 하나라도 빠지면 장비를 바꿔도 색이 안 변한다 — smoke 가 6가지를 전부 검사한다.

**★ 스케줄러는 `setTimeout` 이다. rAF 를 쓰면 안 된다** — 화면이 합성되지 않는 동안
영영 안 와서 카드가 「재는 중」에 갇힌다. 브라우저 검증에서 실제로 잡혔다.

### 24.7 실측 (브라우저)

| | |
|---|---|
| 첫 렌더 | 32ms (전부 「재는 중」) |
| 전부 확정 | 200ms 이내 (숨은 탭·1초 스로틀 상태에서도 1.06초) |
| 재방문 | 8ms · 「재는 중」 없음 (캐시 적중) |
| 부대 변경 | 즉시 「재는 중」 으로 되돌아감 (무효화 정상) |

적 배율을 올려 가며 전이를 훑으면 `x15.1 → 100%` / `x15.4 → 55%` / `x15.7 → 9%` —
**적 전투력 4% 폭 안에서** 100%가 0%가 된다. 그 안에서는 「여유」·「적정」도 정상적으로 뜬다.

### 24.8 남은 것 — 이게 2번(전투 자체)의 근거다

`dangercheck` 이 부대 7종 × 도시 5곳(175건)을 훑은 **밴드별 검사 건수**:

```
식은 죽 먹기  144건
여유            1건
적정            0건
위험            0건
무모           30건
```

**중간 색이 사실상 존재하지 않는다.** 예보는 이제 정직하지만, 정직한 답이
"이긴다" 아니면 "진다" 뿐이다. 5단계 색으로 표현할 대상이 아직 없다는 뜻이고,
이건 이진 승패를 없애야(부분 승·부분 패, 예상 손실 표시) 풀린다.
→ 조사 보고서의 **C안**. 되돌릴 수 없는 지점이 많으므로(DATA_VERSION · 던전/탑/나락 인계 ·
랭킹 기록의 의미) 착수 전에 `result.margin` 을 **기록만** 하는 단계로 먼저 정량화할 것.

## 25. C안 사전 계측 — 손실(margin)을 기록만 해 뒀다

§24 에서 난이도 색은 정직해졌지만 **정직한 답이 「이긴다」/「진다」 둘뿐**이라는 게 드러났다
(부대 7종 × 도시 5곳 175건 중 중간 색이 1건). 풀려면 이진 승패를 없애야 하는데
(부분 승·부분 패, 예상 손실 표시) 그건 던전/탑/나락 인계·보상·랭킹까지 건드리는 큰 공사다.

**착수 전에 효과가 있는지부터 쟀다.** 이 절이 그 결과다.

### 25.1 무엇을 넣었나

`src/battle/engine.js` `finish()` 가 `result.margin` 을 채운다:

```js
margin = { allyAlive, allyCount, allyHp, enemyAlive, enemyCount, enemyHp, score }
```

- **읽는 곳이 하나도 없다.** 일부러 그렇게 뒀다 — smoke 가 그걸 검사한다
  (`quest/dungeon/tower/abyss/battle` 중 하나라도 `.margin` 을 읽기 시작하면 실패한다).
- **난수를 안 먹는다.** 이미 정해진 상태를 읽기만 한다.
  → `balance.mjs` 출력이 변경 전후 **완전히 동일**(차이는 벽시계 시간뿐).
  기존 곡선(WAVE_POWER·탑·나락·세트) 전부 유효, DATA_VERSION 그대로.
- **세이브에 안 들어간다.** 탑 등반 + 나락 잠수 후 세이브에 `margin` 문자열이 없음을 확인.

### 25.2 질문과 답 — `node tools/margin.mjs`

> 이진 승패를 연속량으로 바꾸면 플레이어가 보는 양이 실제로 완만해지나?

기준: 손실의 전이 폭이 승패의 전이 폭보다 **2배 이상**. 미만이면 착수하지 마라.

| 웨이브 | 의뢰 | 배수 |
|---|---|---|
| 1 | q_greenhold_30_0 | 5.11 |
| 1 | q_greenhold_30_2 | 3.48 |
| 2 | q_greenhold_30_1 | 5.14 |
| 2 | q_elderoak_120_0 | 6.67 |
| 3 | q_elderoak_120_3 | **2.68** |
| 3 | q_elderoak_120_1 | 6.41 |

**최악 2.68배 · 평균 4.91배 → 통과.** (n=60 에서 2.72 — 표본을 바꿔도 안 흔들린다.)

★ **평균이 아니라 최악으로 판정한다.** 한 의뢰가 6배 넓다고 3웨이브 의뢰가
  2.7배인 걸 덮을 수 없다 — 플레이어는 그 의뢰도 본다.

### 25.3 도구를 두 번 고쳤다 (숫자를 믿기 전에)

1. 처음엔 **마지막 전투의 `margin.score` 만** 봤다. 그랬더니 패배 구간에서 값이
   위아래로 튀었다(-0.905 → -0.420 → -0.649). 2웨이브에서 진 판이 1웨이브에서 진 판보다
   낮게 찍힌 것이다 — **어디까지 갔는지가 빠져 있었다.**
   → `score = (넘긴 웨이브 수 + 마지막 전투의 남은 아군 전력) / 전체 웨이브 수` 로 바꿨다.
   0 = 1웨이브 전멸, 1 = 무손실 완주. 단조로워졌다.
2. 처음엔 웨이브 모양당 **1건**만 봤다. 3웨이브가 1.63배로 나와 하마터면 착수를 접을 뻔했는데,
   그게 위의 집계 버그였다. 지금은 모양당 2건씩 본다.

### 25.4 데이터가 말해 주는 것

3웨이브 의뢰의 온전도 곡선(적 배율 ↑):

```
 2.00  100%  1.000   ← 무손실
 3.06  100%  0.938   ← 이기지만 조금씩 깎인다
 3.15  100%  0.920
 3.23   45%  0.752
 3.32    5%  0.673
 3.41    0%  0.661
 3.50    0%  0.333   ← 2웨이브에서 전멸 (계단)
```

- **완만한 구간은 대부분 "이기는 쪽"에 있다** (1.000 → 0.920). 즉 연속화의 실질 효과는
  "겨우 이겼다 / 3명 잃고 이겼다" 를 구분해 주는 것이다 — 원하던 바로 그것이다.
- 패배 쪽은 웨이브 경계에서 **계단**이 남는다(0.661 → 0.333). 웨이브 단위로만 진행이
  기록되기 때문이다. 이건 연속화만으로는 안 없어진다.

### 25.5 다음 단계 (C안 착수 시)

되돌릴 수 없는 지점이 많으므로 **한 번에 하나씩**, 각 단계 뒤에 전체 재측정:

  던전 HP 인계(`dungeon.js:748`)·탑 등반·나락 심층을 같이 봐야 한다.

## 27. 3b — 실패 경험치 연속화 + 랭킹 리셋 (DATA_VERSION 5)

### 27.1 제작자 결정

| 물음 | 답 |
|---|---|
| 부분 패에 뭘 주나 | **경험치만.** 보수·명성·전리품은 실패 그대로 0 |
| 실패한 의뢰 재도전 | 지금 그대로 (건드리지 않음) |
| 랭킹 | 시즌 병기 없이 **그냥 리셋** |

골드를 주면 수급이 늘어 earlygame 경제·나락 수입표·랭킹 골드 상한(`rules.js`)을 전부
다시 재야 하는데, 「헛되지 않았다」는 느낌은 경험치만으로도 난다.

### 27.2 무엇을 바꿨나

`quest.js questRewards` 의 패배 보상이 **일괄 25%** 였다. 그래서 1웨이브에서 전멸한 판과
마지막 웨이브를 코앞에서 놓친 판이 똑같았다.

```js
진행도 = (넘긴 웨이브 수 + 마지막 전투에서 남은 아군 전력) / 전체 웨이브 수
경험치 몫 = LOSS_EXP_FLOOR(0.17) + LOSS_EXP_SPAN(0.55) × 진행도
```

「남은 아군 전력」은 인원과 체력을 반씩 본다 — `engine.js result.margin` 과 같은 정의다.

★ `questProgress` 는 **처음 진 웨이브에서 멈춘다.** 진행도를 안 넣고 마지막 전투의
  margin 만 보면 비단조가 나온다 (2웨이브에서 진 판이 1웨이브에서 진 판보다 낮게 찍힌다).

### 27.3 상수는 **총량이 예전과 같도록** 실측으로 잡았다

패배 338건 기준:

| | 옛 (일괄 25%) | 새 | |
|---|---|---|---|
| **총 경험치** | 3,815,459 | 3,817,485 | **+0.1%** |
| 진행도 0.0~0.1 (1웨 전멸) | 11,937 | 9,282 | 0.78배 |

### 27.4 랭킹 리셋

**DATA_VERSION 4 → 5.** 마이그레이션에서 `tower.best/bestDay` · `abyss.best/bestDay` 를 0 으로 내린다.

★ **`stats.questsDone` 은 안 건드린다.** 순위 지표이기도 하지만 `progress.js` 의

  「첫 의뢰를 받아라」가 다시 뜬다. 탑·나락 기록은 순수한 기록이라 그런 부작용이 없다.

★ **`RANK_RESET_VERSION = 5` 로 가둬 뒀다.** `DATA_VERSION` 을 올릴 때 **같이 올리지 마라** —
  같이 올리면 앞으로 수치를 손볼 때마다 남의 기록이 매번 날아간다.

★ 서버 쪽은 `db/005_reset_scores.sql`. **지우지 않고 `scores_history` 로 옮긴다** —
  비용이 같은데 되돌릴 수 있는 쪽은 하나뿐이고, 곡선을 바꾼 뒤 "예전엔 몇 층까지 갔었나"를
  비교할 일이 반드시 생긴다.

**순서: 배포가 먼저, SQL 이 나중.** `scores_monotonic` 트리거는 기록이 줄면 **예외를 던진다**.
클라이언트가 0 을 올리는데 서버에 옛 행(379층)이 남아 있으면 그 사람 제출이 계속 거부된다.
행을 지우면 UPDATE 가 아니라 INSERT 라 트리거를 안 탄다 — 저절로 풀린다.
(순서가 뒤집혀도 망가지진 않는다. 잠깐 제출이 실패하고 재시도가 복구한다.)

리셋 직전 실측: 등재 4명 · 나락 기록 2명(최고 70심층) · 탑 기록 2명(최고 379층) · 세이브 7개.

### 27.5 ★ 이빨 없는 검사를 하나 발견했다

「이미 버전 5 면 기록을 안 건드린다」 검사를 넣었는데, 관문(`cur < 5`)을 **지워도 안 터졌다.**
`migrateDataVersion` 이 `cur === DATA_VERSION` 이면 맨 위에서 반환하기 때문이다 —
지금 버전에서는 관문이 있으나 없으나 결과가 같다.

정작 위험한 건 **미래**다(6 으로 올릴 때 같이 따라 올라가는 것). 그건 실행으로 못 재므로
`RANK_RESET_VERSION` 을 값으로 못 박고 smoke 가 그 값을 검사한다.
남긴 두 검사(리셋이 실제로 일어나는가 / questsDone 을 안 건드리는가)는 이빨을 확인했다 —
리셋을 지우니 첫 번째가 터졌다.

3c 착수 직전에 「확실히 이기는 의뢰가 비용으로 갈리나」를 쟀더니
**138건 중 133건이 무손실(잔여 체력 98%)** 로 나왔다. 그대로 믿었으면
"재료가 없으니 3c 는 무의미하다" 고 결론 냈을 것이다.

**그 측정이 틀렸다.** 고정 부대(F Lv20 … S Lv80)를 전 도시에 붙였기 때문이다 —
조합 대부분이 압승 아니면 압패다. 실제 플레이어는 자기 수준에 맞는 도시를 본다.
`balance.mjs` 처럼 **권장 레벨 부대**로 다시 재니 그림이 완전히 달랐다:

| 랭크 | 승률 | 무손실승 | 1명↓ | 2~3명↓ | 4명+↓ | 패배 |
|---|---|---|---|---|---|---|
| F | 100% | **100%** | 0% | 0% | 0% | 0% |
| E | 77% | 21% | **35%** | 12% | 9% | 23% |
| D | 81% | 2% | 25% | **47%** | 7% | 19% |
| C | 60% | 13% | 3% | 26% | 17% | 40% |
| B | 54% | 14% | 0% | 25% | 15% | 46% |
| A | 66% | 0% | 2% | 24% | **40%** | 34% |
| S | 0% | — | — | — | — | **100%** |

중간은 **손실 축에** 있었다. 승패 축에는 원래 없었다.

→ `tools/dangercheck.mjs` 도 같은 병을 앓고 있어서 권장 레벨 방식으로 고쳤다.

### 28.2 ★★ 공용화하다 버그를 넣었다 — 인계는 **누적**해야 한다

`balance.mjs` 가 웨이브 인계를 손으로 복사해 갖고 있길래 공용 함수로 합쳤는데,
`readWaveCarry(b.units, {})` 로 **매 웨이브 새 인계**를 만들었다. 그러면:

```
1웨이브에서 쓰러짐 → 2웨이브 편성에서 빠짐 → 2웨이브 units 에 없음
→ 새 인계에 항목이 없음 → 3웨이브에서 applyWaveCarry 가
  "인계에 없으니 처음 나온 사람" 으로 보고 **만피로 세운다**
```

3웨이브 의뢰가 쉬워져 B 66.7% · A 63.3% 로 랭크 목표가 깨졌다.
**옛 사본이 옳았고 내 공용화가 틀렸다.** 올바른 쓰임은:

```js
carry = readWaveCarry(b.units, carry || {});     // ← 앞 인계에 누적
```

`readWaveCarry` 문서에 못 박고, smoke 에 검사 3개를 넣었다
(마지막 검사는 "새 객체로 만들면 되살아난다" 를 **일부러** 확인한다 — 계약의 근거다).
전 호출부를 훑어 확인했다: `forecast.js` · `ui/battle.js` · `dangercheck` · `margin` 은 원래 맞았다.

### 28.3 색 규칙

```
승률 0.15 미만                → 무모
승률 0.75 미만                → 위험      (손실과 무관 — 이길지 질지 모른다)
이기고 쓰러짐 3.5명 이상       → 위험      (이겨도 절반이 눕는다)
이기고 쓰러짐 1.5명 이상       → 적정
이기고 쓰러짐 0.5명 이상       → 여유
이기고 무손실                 → 식은 죽 먹기
```

손실은 **이긴 판만** 평균낸다. 화면이 묻는 건 "이기면 몇 명 남나" 라서,
진 판을 섞으면 그 답이 안 된다.

### 28.4 화면

카드에 색 옆으로 한 줄이 붙는다.

```
적정          2.2명쯤 쓰러진다 · 체력 45% 남음
식은 죽 먹기   무손실로 끝낸다 · 체력 96% 남음
무모          이 부대로는 못 이긴다
```

★ **「부상」 이라고 쓰면 안 된다.** 부상은 **실패했을 때만** 난다 (`quest.js` 부상 판정).
  이기면 쓰러진 사람도 낮은 체력으로 그냥 돌아온다. 그래서 「쓰러진다」 라고 쓴다.

★ **승률을 숫자로 안 보여 준다.** 실제 전투는 이미 결정론이라(같은 부대·같은 의뢰면
  결과가 항상 같다 — §24) 「62%」 는 정직한 표현이 아니다. 재는 건 **여유**다.

### 28.5 결과 — 색이 실제로 5개로 갈린다

`dangercheck` (권장 레벨 부대 × 등급 6종 × 도시 5곳, 150건):

| 여유 | 0 | **9** |
| 적정 | 0 | **16** |

| 무모 | 29 | 40 |

중간 3색이 1건 → **30건(20%)**. 예보가 참 승률과 어긋난 건 **150건 중 0건**.

### 28.6 남은 것

- **S랭크 승률이 0%** 로 나온다 (`balance.mjs` 목표는 40~56%). 표준 부대 구성 방식이

  **필요성을 다시 판단해야 한다** — 지금은 안 해도 될 가능성이 높다.

## 29. ★ 난이도 곡선이 «장비» 를 감안하지 않는다 (제작자 제보)

제작자가 실제 플레이 중에 물었다 — *"평균 Lv80 · 전투력 88,043 · 10/10칸 풀장비인데
S급 의뢰(S- 권장 Lv57, S+ 권장 Lv77)를 쉽게 깬다. 3명짜리 5부대도 깬다. 맞나?"*

**라벨은 정확했다.** 예보는 실제로 돌려 보고 「식은 죽 먹기」라고 쓴 것이다.
문제는 그게 사실이라는 것 — 그리고 **왜** 사실인가다.

### 29.1 원인: 모든 난이도 목표가 «장비 없는 부대» 기준이다

`tools/balance.mjs` 의 표준 부대(`stdSquad`)는 **장비가 하나도 없다.**
랭크별 승률 목표(F 88~100 … S 40~56)가 전부 그 맨몸 부대 기준으로 잡혀 있다.

장비 배율 (4차 Lv80 7인, `node tools/gearcheck.mjs`):

| 구성 | 전투력 | 배수 |
|---|---|---|
| 장비없음 · B | 46,615 | ×1.00 |
| 장비없음 · S | 61,081 | ×1.31 |
| 전설10칸 · B | 67,891 | ×1.46 |
| 전설10칸 · S | **82,359** | **×1.77** |

제작자 제2부대가 88,043 이다 — 전설 10칸 S등급보다도 위다(세트 효과가 더 얹혀서).
**난이도 기준선의 1.9배**로 플레이하고 있는 셈이다.

### 29.2 ★★ 전투력 숫자는 난이도를 못 맞힌다

S+ 의뢰(권장 Lv73~79) 완주율:

| 부대 | 전투력 | 완주 |
|---|---|---|
| 7인 · Lv77 · B · 장비없음 (**balance 기준선**) | 45,094 | **0%** |
| 7인 · Lv80 · B · 장비없음 | 46,615 | 0% |
| 3인 · 같은 구성 · 장비없음 (대조) | 17,733 | 0% |
| **2인** · Lv80 · A · 전설10칸 | **21,598** | **100%** |
| 3인 (Lv80×2 + Lv36×1) · A · 전설10칸 | 25,108 | 100% |
| 7인 · Lv80 · A · 전설10칸 | 74,148 | 100% |

**2명(21,598)이 7명(46,615 — 2.2배)이 못 깨는 걸 100% 깬다.**
전투력 합은 난이도의 잣대가 아니다. 장비가 붙은 소수 정예가 맨몸 다수를 압도한다.

→ §24 에서 카드 색을 전투력 비율에서 **실제 시뮬**로 바꾼 것이 결과적으로 옳았다.
  그 숫자를 계속 믿었으면 이 격차를 영영 못 봤다.

### 29.3 콘텐츠 천장이 없다

정예(보상 ×2.2) S 의뢰조차:

| 부대 | 정예 S 완주 |
|---|---|
| 7인 · Lv80 · A · 전설10칸 | **100%** |
| 3인 · Lv80×2+Lv36 · 전설10칸 | 63% |
| 2인 · Lv80 · 전설10칸 | 33% |

**7인 풀장비에게는 가장 어려운 의뢰도 100% 다.** 의뢰 콘텐츠에 엔드게임이 없다.
(탑·나락은 별개로 존재한다 — 거기는 아직 유효하다.)

### 29.4 고치려면

1. **기준선을 다시 잡는다 (근본).** `balance.mjs stdSquad` 에 «그 레벨대의 표준 장비»를
   입히고 랭크 목표를 다시 맞춘다. 그 다음 `RANK_POWER`/`SUB_POWER` 를 재조정.
   — 곡선 전체가 움직이므로 dungeon/tower/abyss/setspecial 전부 재측정이다.
2. **S 위에 콘텐츠를 얹는다.** 새 랭크나 정예 위 단계.
3. 플레이어 전투력에 맞춰 의뢰를 스케일 — **권하지 않는다.** 성장의 보람이 사라진다.

★ 1번이 근본이지만 크다. 2번이 싸고 즉효다. 제작자 결정이 필요하다.

## 30. 도시를 난이도 축으로 — 개편 설계 (진행 중)

§29 에서 "난이도가 장비를 감안 안 한다 / 의뢰에 엔드게임이 없다" 가 드러났다.
제작자가 내놓은 해법이 지금까지 나온 것 중 가장 낫다:

> 도시마다 F~S 를 다 내보내고, **도시 등급이 배율**을 갖는다.
> 명물 클래스도 등급 수만큼(1등급 1종 … 5등급 5종) 둔다.
> 나중에 상위 도시를 얹으면 엔드게임이 자연히 늘어난다.

**왜 좋은가** — 절벽(§24)을 없애려 들지 않고 **콘텐츠로 쓴다.** 탑·나락이 엔드게임에서
아직 유효한 이유와 같다. 플레이어가 의뢰마다 난이도를 고르는 귀찮음도 없다.
S등급 용병도 초반엔 어렵고(1등급 도시 명물 1종) 뒤로 갈수록 수월해진다(5등급 5종) —
나중에 S 위 등급을 얹을 때 눈금도 이미 있다.

### 30.1 ✅ 끝난 것 — 명물 수 = 도시 등급

42칸(도시 등급 합) ÷ 1차 클래스 7종 = **정확히 6** 이라 완전 균등이 가능했다.

| 클래스 | 도시 수 |
|---|---|
| 방패병·검사·창병·도적·궁수·견습마법사·수도사 | **각 6** (편차 0) |

★ 기존 검사 두 개가 첫 시도를 잡았다 — **편차 3** 이었고 **수도사가 1~2등급 도시에
  하나도 없었다**(초반에 힐러를 못 구한다). 손으로 다시 맞춰 편차 0 · 전 클래스 초반 거점 확보.
★ 설명문이 명물을 문장으로 명시하고 있어서 같이 고쳤다. 데이터만 바꾸면 도시 소개가 거짓말이 된다.
★ smoke 규칙도 «1~2종» → «명물 수 = 등급» 으로 갱신했다.

### 30.2 남은 것 — 순서대로

1. **도시 배율 `CITY_POWER` 신설.** 지금은 난이도가 랭크에만 실려 있다.
   실측 사다리(그 시점 기대 스펙의 완주율):

   | 스펙 | 전투력 | ×1.0 | ×1.6 | ×2.0 | ×2.5 |
   |---|---|---|---|---|---|
   | 1등급 도착 (Lv8·F·무장비) | 2,893 | 60% | 60% | 40% | 20% |
   | 3등급 도착 (Lv38·D·6칸) | 22,311 | 100% | 20% | 20% | 20% |
   | 5등급 도착 (Lv72·B·10칸) | 67,323 | 100% | 80% | 0% | 0% |
   | 엔드게임 (Lv80·A·10칸) | 74,148 | 100% | 100% | 33% | 0% |

   → 대략 `{1:1.00, 2:1.15, 3:1.30, 4:1.50, 5:1.75}` 자리이고 6·7등급은 2.0/2.3 쯤.
   **다만 이 표는 랭크가 섞여 노이즈가 크다. 상수를 박기 전에 랭크 고정으로 다시 재라.**
   ★ 배율은 **제곱으로 먹는다** — hp·atk·def·res 에 전부 곱하면 실효가 배율² 에 가깝다
     (`ELITE_MULT` 이 1.30→1.035 로 내려간 이유가 이것이다). 반드시 실측으로 정해라.

2. **`RANK_WEIGHT` 를 전 도시 F~S 로.** 지금은 등급별로 랭크 창이 좁다
   (1등급은 F/E/D 만, 5등급은 C/B/A/S 만).

3. **★★ 보상이 도시 배율을 따라가야 한다.** 안 그러면 같은 S랭크를 1등급 도시에서만 돈다.
   `questRewards` 의 골드·경험치·전리품 ilvl 에 `CITY_POWER` 를 반영해라.
   **이걸 빼먹으면 개편 전체가 무의미해진다.**

4. **의뢰 수 증량** (`QUEST_COUNT_MAX` 16 → ?). 도시마다 F~S 가 다 나오려면 지금 수로는 얇다.

5. **재측정 전부** — `balance.mjs` 의 랭크 목표가 «도시 배율 없음» 기준이라 정의가 바뀐다.
   랭크별이 아니라 **(랭크 × 도시 등급)** 으로 목표를 다시 세워야 한다.

### 30.3 되돌릴 수 없는 지점

- `RANK_WEIGHT`/`CITY_POWER` 를 바꾸면 **DATA_VERSION 을 올려야** 한다 (의뢰 목록이 새 규칙으로 다시 채워져야 하므로).
- 곡선 파일을 건드리면 `syncshared` + `supabase functions deploy submit-score` 가 따라온다.

## 31. 지역 등급으로 통일 + 도시 2개 추가 + 명물/S확률 재설계

### 31.1 ★ 등급이 두 벌이었다

화면의 「1등급」은 **지역** 등급인데, 주점 확률(`effectiveTier`)은 **도시** `tier` 를 쓰고 있었다.
14개 중 6개가 어긋나 있었다 (왕의안식 지역1/도시2, 잿불우물 지역4/도시5 …).
플레이어에겐 「1등급 지역인데 왕의안식만 좋은 용병이 나오네?」로 보인다 — 설명 없이는 알 수 없다.

→ **도시 `tier` 를 지역 등급으로 통일했다.** 필드는 남겨 뒀다(나중에 거점 차등이 필요하면 되살린다).

### 31.2 새 구조 (제작자 설계)

| 지역등급 | 도시 | 명물/도시 | S 상한(평판 만점) | S 시작(평판 10) |
|---|---|---|---|---|
| 1 | 3 | 1 | 3.0% | 0.60% |
| 2 | 4 | 1 | 3.0% | 0.60% |
| 3 | 4 | 2 | 4.0% | 0.80% |
| 4 | 2 → **3** | 3 | 4.5% | 0.90% |
| 5 | 1 → **2** | 4 | 5.0% | 1.00% |

★ **1·2등급의 7칸에 7클래스가 정확히 하나씩** 들어간다. 그래서
  「모든 클래스가 초반 거점을 갖는다」가 규칙이 아니라 **구조에서 저절로** 나온다.
  (§30 에서는 이걸 손으로 맞춰야 했고, 첫 시도에 수도사가 빠져 검사에 걸렸다.)

★ 32칸 ÷ 7클래스 = 4.57 → 클래스별 4~5개 도시 (편차 1).

### 31.3 S 확률: 도시가 천장, 평판이 차오름

예전에는 상한이 `SPEC_S_MAX` 0.05 하나였고 **실효 티어**(도시+평판+특화 혼합)에 비례했다.
그래서 5등급 명물 도시가 **평판 10 에서 이미 3.6%** 였다 — 도착하는 순간 거의 상한이라
평판이 S 확률에 사실상 안 먹었다.

지금은 `SPEC_S_MAX_BY_TIER` 가 천장을 정하고 평판이 `SPEC_S_START_FRAC`(20%)에서
100% 까지 차오른다. 실측이 표와 한 자리도 안 어긋난다.

### 31.4 새 도시

- **모래시계** (태양흉터 황야, 4등급) — 대상로가 갈라지는 바위 그늘. 궁수·방패병·도적.
- **마지막 등불** (서리변경, 5등급) — 서리관문 **너머**. 견습마법사·궁수·도적·수도사.
  ★ 관문을 지나야만 닿는 **유일한 길**로 뒀다 (`frostgate ↔ lastlamp` 만 연결).
  서리관문 설명의 "북쪽 전부를 막아선다" 는 "— 성벽 안쪽으로는" 을 붙여 살렸다.

### 31.5 ⚠ 남은 문제 — 좁은 폭 라벨 겹침

`node tools/maplabels.mjs` 가 **2개 폭에서 FAIL** 한다 (겹침 12쌍, 그 폭에서 표시 라벨 4개).
도시가 14 → 16 이 되면서 배치기가 못 푸는 밀도가 됐다. 넓은 폭은 0쌍으로 통과한다.

★ 변경 전에는 통과했다 — **이 개편이 만든 것이다.** 위치를 세 벌 바꿔 봤지만 안 풀렸다.
  선택지: (a) 좁은 폭에서 라벨 표시 개수를 더 줄인다 (b) 배치기에 회피 방향을 늘린다
  (c) 도시 좌표를 더 크게 재배치한다. **(a)가 가장 싸다.**
  ※ `tools/maplabels.mjs` 는 `worldmap.js` 와 상수가 다르다는 기존 메모가 있다 —
    고치기 전에 **실제 화면에서 정말 겹치는지** 먼저 확인해라.

### 31.6 남은 단계

§30.2 의 나머지 — **도시 배율 `CITY_POWER`** 와 **보상 연동**, **전 도시 F~S**(`RANK_WEIGHT`).
실측한 55% 지점: 2등급 ~×1.15 / 3등급 ~×1.5 / 4등급 ~×1.4 / 5등급 ~×1.7.
★ 배율 ×1.0(지금)에서 각 등급의 기대 스펙이 이미 **86~100%** 다 — §29 의 «장비 미반영» 이
  5등급뿐 아니라 **전 구간**에 걸쳐 있다는 뜻이다.

## 32. 지도 라벨 — 뱃지도 placeLabel 로 (전 폭 0쌍)

§31.5 의 겹침을 끝냈다. 원인이 둘이었고 **둘 다 «두 벌» 문제**였다.

### 32.1 도구가 옛 코드를 재고 있었다

`tools/maplabels.mjs` 가 `worldmap.js placeLabel` 의 후보 목록을 **손으로 복사**해 갖고 있었다.
게임 쪽을 6 → 12 곳으로 늘렸는데 도구는 6 그대로라 **개선이 측정에 전혀 안 잡혔다.**
좌표를 여섯 벌 바꿔 가며 "안 풀린다" 고 결론 낼 뻔했다.

### 32.2 뱃지가 간선 중점에 **고정**이었다

도로 일수 뱃지는 `lerp(...0.5)` 로 중점에 박혀 피할 방법이 없었다.
짧은 간선이 몰린 곳(사막에 도시를 하나 더 놓으면서)에서 뱃지끼리 124쌍이 겹쳤다.

→ 뱃지도 `placeLabel` 로 자리를 찾고, **없으면 안 그린다.**
  겹쳐서 둘 다 못 읽느니 하나를 지우는 편이 낫고,
  같은 정보가 도시 라벨 둘째 줄(「3일」)에 이미 있다.

### 32.3 결과

| 폭 | 이전 | 지금 | 표시 라벨 |
|---|---|---|---|
| 폰 360px | 12쌍 | **0쌍** | 4 |
| 폰 390px | 12쌍 | **0쌍** | 4 |
| 태블릿 | 124쌍 | **0쌍** | 88 (이전 69) |
| PC | 124쌍 | **0쌍** | 90 (이전 67) |

겹침이 사라지면서 **표시되는 라벨이 오히려 늘었다** (67 → 90).
자리를 못 찾아 버려지던 라벨들이 이제 대각선·먼 좌우로 비켜서 들어간다.

★ `placeBox` (도구) 와 `placeLabel` (게임) 의 후보 목록은 **반드시 같아야 한다.**
  어긋나면 도구가 조용히 거짓말을 한다 — 이미 한 번 겪었다.

## 33. 명물 클래스를 지도에 (고른 도시 · 넓은 화면만)

제작자 지적: 「지도에서 명물 클래스가 안 보인다」.

### 33.1 왜 «고른 도시에만» 인가

전부에 붙이면 라벨이 한 줄씩 길어져 §32 에서 0쌍으로 맞춰 놓은 겹침이 되살아난다.
실측으로 확인했다:

| 붙이는 범위 | 폰 | 태블릿·PC |
|---|---|---|
| 현재+고른+가리킨 곳 (3줄 라벨) | 10쌍 | 30쌍 |
| 고른 곳만 (3줄 라벨) | 6쌍 | 8쌍 |
| 고른 곳만 · **별도 라벨** | 3~4쌍 | **0쌍** |
| 고른 곳만 · 별도 라벨 · **폰 제외** | **0쌍** | **0쌍** |

### 33.2 ★ 셋째 줄이 아니라 «별도 라벨» 인 이유

도시 라벨은 `force` 다 — 자리가 없어도 그린다(현재 위치·고른 곳은 무조건 보여야 하니까).
거기에 셋째 줄을 붙이면 **커진 라벨이 자리를 무시하고 그려져** 겹친다.

명물을 별도 라벨(`force: false`)로 떼면 자리가 없을 때 **이것만 조용히 빠진다.**
도시 이름은 그대로 보이고 명물만 안 보이는 것 — 잃는 게 가장 적은 실패다.

### 33.3 폰에서 빼는 이유

폰은 표시 라벨이 4개뿐인데 한 줄을 더 넣으면 그마저 겹친다.
그리고 **폰은 지도 아래 「인접 도시」 목록에 이미 명물이 나온다** — 중복이다.

★ 도구(`maplabels.mjs`)도 같은 규칙을 알아야 한다. 명물 줄을 게임에만 넣고 도구에
  안 넣으면 라벨 높이를 잘못 재서 겹침 보고가 통째로 틀린다 (§32 에서 겪었다).

## 34. 도시 배율 `CITY_POWER` + 전 도시 F~S (DATA_VERSION 6)

§30 의 남은 단계다. 도시(=지역) 등급이 **난이도 축**이 됐다.

```js
CITY_POWER      = { 1: 1.00, 2: 1.15, 3: 1.32, 4: 1.50, 5: 1.70 };
CITY_REWARD_POW = 2.0;      // 보상 = 배율 ^ 2  (5등급 ≈ 2.89배)
```

- 배율은 **생성 시점**에 `wave.power` 로 들어간다. 모든 소비자(전투·예보·도구)가 같은 값을 본다.
- `RANK_WEIGHT` 를 열어 **전 도시가 F~S** 를 다 낸다. 본토 대역은 여전히 압도적이다
  (1등급 도시: F 55% … S 1.0% / 5등급: F 1.7% … S 14%).
- **보상이 배율을 따라간다.** 안 하면 다들 1등급 도시에서 S랭크만 돈다.
  전리품은 개수가 아니라 **ilvl** 을 √배율 만큼 올린다 (개수를 늘리면 가방이 터지고
  등급 곡선이 흔들린다). 명성은 랭크가 정한다 — 도시로 부풀리지 않는다.

### 34.1 ⚠ `balance.mjs` 가 FAIL 한다 — 기준선이 낡았다

| 랭크 | 맨몸 부대(balance 기준) | **장비 갖춘 부대** | 목표 |
|---|---|---|---|
| F | 100% | 100% ✓ | 88~100 |
| E | 51% | 74% ✓ | 72~86 |
| D | 17% | 64% ✓ | 62~78 |
| C | 13% | 11% ✗ | 55~70 |
| B | 5.6% | 85% ✗ | 48~64 |
| A | 5.9% | 62% ✗ | 44~60 |
| S | 1.1% | 36% ✗ | 40~56 |

**`balance.mjs stdSquad` 는 장비가 하나도 없다** (§29). 개편은 «장비를 감안한 난이도» 로
가는 것이므로, 맨몸 기준의 목표 대역은 **정의가 낡았다.** 장비를 입혀 재면 F·E·D 가
통과하고 A·S 도 근접한다 — 즉 `CITY_POWER` 자체는 대체로 맞는 자리에 있다.

C 11% / B 85% 는 **내가 가정한 장비 사다리**가 전직 경계(Lv35)에서 계단이라 생긴 것으로 보인다
(Lv30 은 2차 클래스 5칸, Lv40 은 3차 8칸). 게임의 실제 성장 곡선과 맞는지 확인이 필요하다.

**다음 (필수)**: `balance.mjs stdSquad` 에 «그 레벨대 표준 장비» 를 입히고
랭크 목표를 다시 세운 뒤, 그 잣대로 `CITY_POWER` 를 미세 조정해라.
그 전까지 `balance.mjs` 의 랭크 판정은 **믿으면 안 된다.**

### 34.2 안 건드린 것

던전·탑·나락은 자체 곡선(`WAVE_POWER`/`tower.js`/`abyss.js`)이라 `CITY_POWER` 와 무관하다 — 확인했다.
`RANK_RESET_VERSION` 은 **5 에 고정**이다. DATA_VERSION 6 으로 올려도 랭킹은 다시 리셋되지 않는다.

## 35. `balance.mjs` 기준 부대에 장비를 입혔다 — 전 랭크 목표 통과

§34 에서 «맨몸 기준선이 낡았다» 고 적어 둔 걸 고쳤다.

### 35.1 무엇을 바꿨나

`allyDef` 가 `mercStats({...equipment: {}}, null)` 로 **맨몸** 스탯을 쓰고 있었다.
→ `gearedMerc()` 로 «그 레벨대에 보통 갖추는» 장비를 입힌다.

| 레벨 | 칸 | 희귀도 보정 |
|---|---|---|
| ~14 | 2 | 0 |
| 15~34 | 5 | +1 |
| 35~54 | 8 | +2 |
| 55~ | 10 | +2 |

전직 경계(15/35/55)와 같은 계단이다. 풀세트를 주면 이번엔 반대로 너무 쉬워진다.
★ `(클래스·레벨·등급)` 으로 캐시해 **항상 같은 장비**를 준다 — 측정이 시드마다 흔들리면 안 된다.

### 35.2 CITY_POWER 를 그 잣대로 다시 맞췄다

**목표 대역은 손대지 않았다.** 설계 의도(F 쉽고 S 어렵다)는 그대로 두고 배율만 옮겼다.

| 배율 사다리 | D | C | B | A | S |
|---|---|---|---|---|---|
| 1.15/1.32/1.50/1.70 | 60.7 | 54.4 | 44.1 | 33.7 | 44.1 |
| 1.10/1.24/1.38/1.55 | 76.7 | 70.7 | 77.4 | 68.1 | 50.7 |
| **1.13/1.28/1.44/1.63** | **66.3** | **62.2** | **58.9** | **48.1** | **47.4** |
| 목표 | 62~78 | 55~70 | 48~64 | 44~60 | 40~56 |

**★★ 배율 5% 차이가 승률을 30%p 흔든다.** (B: 44.1% → 77.4%)
§24 의 절벽이 그대로 살아 있다는 뜻이다 — **이 상수는 눈으로 정하면 안 된다.**
건드릴 때마다 `node tools/balance.mjs` 로 전 랭크를 다시 봐라.

### 35.3 최종

```js
CITY_POWER = { 1: 1.00, 2: 1.13, 3: 1.28, 4: 1.44, 5: 1.63 };
```

| 랭크 | F | E | D | C | B | A | S |
|---|---|---|---|---|---|---|---|
| 승률 | 100 | 84.4 | 66.3 | 62.2 | 58.9 | 48.1 | 47.4 |
| 판정 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

`dangercheck` 도 150건 중 어긋남 0 — 예보가 새 곡선에서도 정확하다.
